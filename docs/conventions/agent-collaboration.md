# 멀티 에이전트 협업 프로토콜

루트 [AGENTS.md](../../AGENTS.md)가 흐름을, 이 문서가 **포맷과 판정 기준**을 정의한다.

## 1. 작업 티켓 포맷 — `.worktrees/tickets/T-<n>.md`

```markdown
---
id: T-12
title: 주 단위 날짜 스트립 컴포넌트
type: feature # feature|fix|refactor|docs|chore|test
branch: feature/date-strip
worktree: .worktrees/date-strip
spec: docs/specs/date-strip.md # 없으면 "none" + 티켓 본문에 요구사항 전문
owns: # 이 티켓이 수정 가능한 파일/글롭. 서로소 규칙 적용
  - src/features/date-strip/**
  - src/domain/date/**
reads: # 시작 전 읽어야 할 것. 여기 없는 문서는 읽지 않음
  - docs/conventions/code-style.md
  - src/features/AGENTS.md
  - src/domain/AGENTS.md
depends_on: [T-10] # 머지 선행 티켓
model: sonnet # 권장 모델
size: S # S(<100줄) M(<300줄) L(스캐폴딩/설정)
---

## 목표 (1~3줄)

## 완료 조건 (체크리스트, 검증 가능한 문장)

- [ ] `DateStrip`이 선택 날짜 기준 ±3일을 렌더한다
- [ ] 좌우 화살표 키로 이동 가능하다 (테스트 포함)

## 범위 밖 (명시적으로 하지 않을 것)

## 참고 (스펙 섹션, 리서치 문서 섹션 헤더만 — 본문 복붙 금지)
```

- `owns:` 없는 티켓은 무효. 오케스트레이터는 발행 전 `BOARD.md`의 진행 중 티켓들과 교집합 검사(절차: §1.1).
- 티켓 번호는 **오케스트레이터가 발행 시점에** `BOARD.md`의 마지막 번호 +1로 부여한다(단조 증가, 삭제된 티켓 번호도 재사용 금지). 로컬 파일이므로 커밋하지 않는다.
- **`owns` 는 티켓을 발행하기 전에 "완료 조건을 만족시키려면 어떤 파일이 바뀌어야 하나" 를 역산해서 채운다.** 두 갈래를 모두 본다:
  1. **스펙이 도메인/공용 위치를 지정한 함수**가 있으면(`<spec>.md` §4 또는 동등한 "데이터·계산" 절) 그 경로를 `owns` 에 반드시 넣는다.
  2. **티켓의 목적을 달성하려면 반드시 고쳐야 하는 진입점·마운트 지점·호출처**를 빠짐없이 넣는다. 새 코드를 어디에 붙이느냐가 아니라 **무엇을 갈아 끼우느냐**로 센다.

  빠지면 구현자는 락 규칙(CLAUDE.md §7-5)을 어기거나 티켓을 완수하지 못하거나 둘 중 하나를 골라야 한다. 실제로 세 번 났다:
  - **T-09**(날짜 요약): `date-strip.md` §4 가 "요약은 도메인 순수 함수"로 지정했는데 `owns` 에 `src/domain/**` 가 없어 계산이 `src/features/date-strip/` 안으로 들어갔다. 리뷰 라운드 1에서 뒤늦게 `src/domain/todo/day-summary.ts` 로 옮겼다.
  - **T-17**(명령 매칭): `shortcuts.md` §4 가 도메인을 지정했는데 T-17·T-19 어느 쪽 `owns` 에도 `src/domain/**` 가 없어 `src/features/command/lib/` 에 갇혔다. 리뷰에서도 못 잡아 별도 후속 티켓이 필요해졌다.
  - **T-20**(앱 셸, PR #33): `owns` 가 `src/features/shell/**` 한 줄뿐이었는데, 이 티켓의 **존재 이유 자체가** `src/app/page.tsx` 의 `<h1>Tasky</h1>` 를 실제 앱으로 바꾸는 것이었다. 즉 도메인 문제가 아니라 **마운트 지점 누락**이다. 구현자는 `owns` 밖인 그 파일을 고치고도 PR 본문에는 "티켓 `owns` 를 그대로 복사했다"고 적어, owns 블록과 셀프 체크리스트가 **둘 다 거짓**이 됐다. 오케스트레이터가 티켓 `owns` 를 확장하고 정정 블록을 남겼다(`.worktrees/tickets/T-20.md`).

- **선행 티켓이 만들 파일에 후행 티켓이 배선해야 한다면, 그 배선 지점을 후행 티켓의 `owns` 에 미리 적는다**(발행 시점에 그 파일이 아직 없어도 경로로 적는다). 또는 선행 티켓의 완료 조건에 "후행 기능의 슬롯을 비워 두고 배선 지점을 핸드오프에 명시"를 넣는다. 둘 다 없으면 **기능이 다 구현되고 테스트도 통과하는데 화면에는 안 뜨는** 상태로 끝난다.
  - **T-19**(커맨드 팔레트)는 앱 셸(**T-20**)보다 먼저 발행돼 `owns` 에 셸 파일이 없었다. 셸이 `<CommandLayer />` 를 `palette` 없이 마운트하므로 `src/features/shell/components/ShellGlobals.tsx` 에 `palette={<CommandPalette />}` **한 줄**이 필요했는데, 그 줄을 넣을 주체가 어느 티켓에도 없었다 — 팔레트는 전부 구현되고 테스트도 통과했지만 사용자는 열 수 없었다. 오케스트레이터가 T-19 의 `owns` 를 그 파일 한 줄 범위로 확장했다(정정 블록: `.worktrees/tickets/T-19.md`).

- **구현자가 `owns` 를 넓혀야 한다고 판단하면 임의로 넓히지 말고 멈추고 보고한다**(§7 에스컬레이션). 넓힌 채로 "티켓대로 했다" 고 PR 본문에 적는 것이 가장 나쁘다 — **락 위반보다 거짓 보고가 더 비싸다.** 락 위반은 diff 대조로 드러나지만, 거짓 보고는 리뷰어가 대조를 건너뛰게 만든다.

### 1.1 owns 교집합 검사 절차 (오케스트레이터, 티켓 발행 전 필수)

1. `BOARD.md`에서 status가 `todo`·`in-progress`·`in-review`·`needs-fix`인 행의 `owns` 열을 모은다.
2. 새 티켓의 `owns:` 글롭과 한 줄씩 비교해 같은 파일/디렉토리를 가리키는 것이 있으면 교집합.
3. 겹치면 두 티켓을 직렬화(`depends_on`)하거나 `owns:`를 재분할해서 겹침을 없앤다.
4. 이 검사는 기계적으로 강제되지 않는다(티켓이 `.gitignore` 대상이라 CI가 못 봄) — 리뷰 시점 검증은 PR 본문 `## owns` 블록과 `git diff --name-only main...HEAD` 대조로 보완한다(AGENTS.md §4).

## 3. 핸드오프 문서 — `.worktrees/handoffs/T-<n>.md`

포맷은 [.worktrees/AGENTS.md](../../.worktrees/AGENTS.md). 추가 규칙:

- 구현 에이전트가 PR 생성 직후 작성. 리뷰 라운드마다 `## Round N 반영` 절을 append.
- 리뷰어는 리뷰 전에 핸드오프의 `decisions:`와 `not-done:`을 읽는다(의도된 미구현을 지적하지 않기 위해).
- **스크래치패드의 검증 스크립트·산출물은 티켓 번호를 파일명이나 디렉토리에 넣는다**(`scratchpad/mutate-t19.py`, `scratchpad/t25-shots/`). 여러 세션이 같은 스크래치패드를 공유하므로 `mutate.py` 같은 일반명은 **말없이 덮어써진다.**
- **변이(음성 대조) 집계는 SKIP 건수를 항상 함께 적는다** — SKIP 을 숨기면 돌지 않은 변이가 "죽었다"로 집계된다. T-19/PR #35 에서 공용 `scratchpad/mutate.py` 를 다른 세션이 덮어써 **중간 집계 한 번이 SKIP 2건을 숨겼다**; 구현자가 알아채고 티켓 전용 이름으로 다시 돌려 `33 죽음 · SKIP 0` 으로 바로잡았다. 이 레포의 고질병이 "가짜 초록불"인데, **검증 하네스 자체가 조용히 오염되면 그걸 잡을 수단이 없다.**

## 4. 병렬 리뷰 라운드 운영

- **소스를 변이하는 리뷰(음성 대조)는 한 워크트리에 한 명만.** 페르소나를 병렬로 돌릴 때 오케스트레이터는 리뷰어마다 **독립 사본**을 주거나(`git archive <sha>` 로 뜬 트리), **변이 리뷰어 1명 + 읽기 전용 리뷰어 N명**으로 갈라 배치한다.
- **리뷰어는 실측이 흔들리면 먼저 오염을 의심한다.** 실측 기반 지적을 쓰기 전에 `git status --porcelain` 이 비어 있는지 확인하고, 아니면 독립 사본에서 다시 잰다. **오염된 관측으로 쓴 지적은 거짓 지적이 되어, 구현자가 없는 버그를 쫓게 만든다.**
  - 근거: **T-20/PR #33 라운드 1** — 오케스트레이터가 리뷰어 3명을 `.worktrees/app-shell` 한 곳에 몰아넣었고, 프론트엔드 리뷰어가 음성 대조로 소스를 **20회 변이·원복**하는 동안 나머지 둘이 같은 트리에서 실브라우저를 띄웠다. **두 리뷰어가 독립적으로 오염을 보고**하고 각자 `git archive HEAD` 로 무오염 사본을 떠 전부 다시 쟀다(한 리뷰어의 초기 관측은 폐기). 알아채지 못했으면 오염된 관측이 근거인 거짓 지적이 그대로 구현자에게 갔다.

### 4.3 심각도 정의

| 태그        | 정의                                                                                                                          | 처리                         |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| **Blocker** | 머지되면 깨짐: 빌드/테스트 실패, 데이터 손상·유실, 레이어 경계 위반, 금지어·author 위반, 락(owns) 위반, 스펙 핵심 요구 미충족 | 필수 수정 + 제기 리뷰어 확인 |
| **Major**   | 동작은 하나 명백한 결함: 버그 가능성, 접근성 기준 위반, 잘못된 상태 구독, 누락 테스트(필수 범위), ADR 위반                    | 수정 또는 근거 있는 거절     |
| **Minor**   | 품질 개선: 가독성, 중복, 성능 미세 개선, 문구                                                                                 | 선택. 거절 시 근거 불요      |
| **Nit**     | 취향/일관성                                                                                                                   | 선택                         |

### 4.4 집계와 "피드백 3개 이하" 정확한 기준

1. 모든 페르소나 보고를 모은다.
2. **중복 제거**: 같은 파일·같은 원인을 두 리뷰어가 지적하면 1개(높은 심각도로 통일).
3. **유효 피드백 수 = Blocker 수 + Major 수** (Minor·Nit는 집계 제외).
4. 판정:
   - `유효 ≤ 3` → **루프 종료**. 구현자는 Blocker 전부 수정(제기 리뷰어에게 해당 항목만 재확인 요청 → `confirmed`), Major는 반영 또는 거절 근거 기재. Minor/Nit는 재량. 오케스트레이터는 CI 녹색 확인 후 머지.
   - `유효 ≥ 4` → 구현자가 Blocker·Major 전부 처리 + Minor 가능한 범위 처리 → **다음 라운드** 전체 리뷰(같은 페르소나 구성).
5. 최대 3라운드. 3라운드 종료 시에도 `유효 ≥ 4`면 오케스트레이터가 사용자에게 보고: (a) 범위 축소 후 머지 (b) 티켓 분할 (c) 폐기.
6. 거절된 Major에 리뷰어가 재반박하면 오케스트레이터가 ADR/스펙으로 판정. 판정 결과는 PR 코멘트에 기록.

### 4.5 오케스트레이터 집계 코멘트 (PR에 라운드당 1개)

```markdown
## Review Round 1 — 유효 피드백 2 (B0/M2/m3/n1) → 종료, 머지 진행

| #   | sev   | 위치             | 요지                    | 처리           |
| --- | ----- | ---------------- | ----------------------- | -------------- |
| 1   | Major | DateStrip.tsx:41 | 스토어 전체 구독        | 반영 (a1b2c3d) |
| 2   | Major | useWeek.test.ts  | 키보드 이동 테스트 누락 | 반영 (d4e5f6a) |
| 3   | Minor | useWeek.ts:12    | useMemo 제거            | 반영           |
```

## 5. 구현자의 피드백 응답 규칙

- 항목별 응답: `반영 <커밋 해시>` / `거절: <근거 1~2줄>` / `후속 T-<n> 제안: <이유>`.
- "확인했습니다", "좋은 지적입니다"만 쓰는 응답 금지.
- 거절은 Major 이하만 가능. Blocker 거절은 오케스트레이터 판정 요청으로만.

## 6. 리뷰 러브릭 (리뷰어 자기 점검, 보고 전 30초)

- [ ] 내 페르소나 범위 안의 항목만 적었다
- [ ] 모든 항목에 파일:줄 + 제안이 있다
- [ ] 심각도를 부풀리지 않았다(Blocker는 "깨짐"일 때만)
- [ ] 핸드오프의 `not-done:`을 다시 지적하지 않았다
- [ ] diff 밖 파일을 읽었다면 이유가 있었다
- [ ] 실측 기반 지적이라면 그 관측을 **오염되지 않은 트리**에서 얻었다(`git status --porcelain` 확인, 아니면 독립 사본)

## 7. 에스컬레이션 규칙

- 구현 중 `owns:` 밖 파일 수정 필요 → 즉시 중단, 오케스트레이터에 파일명+이유 보고.
- 스펙과 리서치 문서가 상충 → 스펙 우선, 오케스트레이터 보고.
- 의존성 추가 필요 → 사용자 확인 필요(CLAUDE.md §7-9). 오케스트레이터가 `chore/deps-*` 티켓으로 분리.
- 아키텍처 변경 필요 → ADR 초안(`docs/decisions/`)을 먼저 PR.
