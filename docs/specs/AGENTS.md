## 스펙 포맷 (150줄 이하)

```text
<!-- 읽기 조건: … -->
# <기능명> 스펙
- 상태: draft | approved | implemented · 관련 ADR: - · 리서치 참조: reference-app-research.md §N
## 1. 목표 (사용자 관점 1~3줄)
## 2. 화면과 인터랙션 (텍스트 와이어프레임, 상태별: 기본/빈 상태/로딩/에러, 데스크탑+좁은 화면)
## 3. 규칙 (검증 가능한 문장으로 번호 매김: "R1. 제목은 1~100자")
## 4. 데이터 (domain 타입 변경 여부, 레포지토리 메서드)
## 5. 접근성 (키보드 흐름, 라벨)
## 6. 범위 밖
## 7. 완료 조건 (티켓 완료 조건의 원본)
```

## 규칙

1. `approved` 상태가 아닌 스펙으로 구현 티켓을 발행하지 않는다(오케스트레이터 책임).
2. 스펙 변경은 구현 PR과 분리(`docs(specs): …`). 구현 중 발견한 스펙 오류는 핸드오프 `decisions:`에 적고 후속 스펙 PR.
3. 레퍼런스 앱 동작은 "레퍼런스 앱에서는 …" 형식으로만 서술. 제품명·스크린샷 금지.
4. 규칙 문장(R-번호)은 테스트명과 1:1 대응을 목표로 한다.
5. 수치(px·ms·자 수·HEX)는 `theme.md`가 단일 소스. 다른 스펙은 토큰 이름으로 참조한다.
6. 구현 방법(컴포넌트·스토어·파일명)은 쓰지 않는다. 그것은 `TECH_PLAN.md`와 티켓의 몫 — 스펙은 "무엇", 구현은 티켓/코드다(가장 흔한 실수).
7. 리서치의 `(추정)` 항목을 그대로 요구사항으로 옮기지 않는다 — 수치는 우리가 정한 값으로 확정해 적는다.
