# docs/specs/ — AGENTS

## 목적
기능별 요구사항 단일 소스. 티켓의 `spec:`이 가리키는 파일. 리뷰어(사용자 관점)의 판정 근거.

## 여기 있는 것 (MVP 예정 목록 — 파일명 고정)
`date-strip.md` · `category.md` · `todo.md` · `completion-rate.md` · `theme.md` · `pwa.md`
Phase 2: `social.md`, `sync.md` (지금은 만들지 않음, 라벨 `phase:2`)

## 스펙 포맷 (150줄 이하)
```markdown
<!-- 읽기 조건: … -->
# <기능명> 스펙
- 상태: draft | approved | implemented    - 관련 ADR: -    - 리서치 참조: reference-app-research.md §N
## 1. 목표 (사용자 관점 1~3줄)
## 2. 화면과 인터랙션 (텍스트 와이어프레임 허용, 상태별: 기본/빈 상태/로딩/에러)
## 3. 규칙 (검증 가능한 문장으로 번호 매김: "R1. 제목은 1~100자")
## 4. 데이터 (domain 타입 변경 여부, 레포지토리 메서드)
## 5. 접근성 (키보드 흐름, 라벨)
## 6. 범위 밖
## 7. 완료 조건 (티켓 완료 조건의 원본)
```

## 규칙
1. `approved` 상태가 아닌 스펙으로 구현 티켓을 발행하지 않는다(오케스트레이터 책임).
2. 스펙 변경은 구현 PR과 분리(`docs(specs): …`). 구현 중 발견한 스펙 오류는 핸드오프 `decisions:`에 적고 후속 스펙 PR.
3. 레퍼런스 앱 동작은 "레퍼런스 앱에서는 …" 형식으로만 서술. 제품명·스크린샷 금지.
4. 규칙 문장(R-번호)은 테스트명과 1:1 대응을 목표로 한다.

## 검증

```bash
bash scripts/check-forbidden-words.sh

```

## 자주 하는 실수
- 구현 방법(컴포넌트 이름, 스토어 구조)을 스펙에 씀 → 스펙은 "무엇", 구현은 티켓/코드.
