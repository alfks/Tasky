# 동기화 스펙

- 상태: approved · 관련 ADR: ADR-0015(accepted, 2026-09-18) · 리서치 참조: reference-app-research.md §4(실시간 동기화, Firebase 추정), §7 User 모델

## 1. 목표

**이것은 기능 추가가 아니라 제품 성격의 변경이다**(ADR-0015 자신의 표현). 로그인 페이지가 먼저 뜨고, 구글 계정으로 로그인해야 앱을 쓸 수 있다 — 그 대신 여러 기기의 데이터가 자동으로 맞춰진다. 이 스펙은 ADR-0015가 이미 확정한 것(신원·권위·동기화 방식·오프라인·기존 데이터 처리)을 화면 규칙으로 옮길 뿐이다. **기술 선택(구글·D1·필수 로그인·준실시간)은 여기서 다시 정하지 않는다** — 그건 ADR-0015의 몫이고 이미 끝났다.

## 2. 화면과 인터랙션

로그인 화면(세션 없으면 **항상 먼저**, 다른 화면을 거치지 않는다):

```
 ┌──────────────────────────────┐
 │          Tasky                │
 │ 하루를 카테고리 색으로 꾸미며   │
 │                                │
 │     [ G  Google로 계속하기 ]   │
 └──────────────────────────────┘
```

첫 로그인 직후, 이 기기에 로그인 전 로컬 데이터가 있으면(ADR-0015 §5):

```
 ┌ 이 기기의 데이터를 계정으로 올릴까요? ─── ✕ ┐
 │ 로그인 전에 이 기기에 저장된 할 일 42개,     │
 │ 카테고리 3개가 있어요.                       │
 │            [ 내보내고 지우기 ] [ 올리기 ]     │
 └──────────────────────────────────────────────┘
```

이 다이얼로그는 전량 삭제를 포함하는 선택지("내보내고 지우기")가 있어 **app-shell.md R14(파괴적 확인 대화상자 공통 규칙)**를 따른다: `role="alertdialog"`, 초기 포커스는 비파괴 선택지인 **[올리기]**("내보내고 지우기"는 초기 포커스·기본 제출 대상이 아니다), `Esc`·✕ = 취소(선택을 보류하고 다음 접속 때 다시 묻는다).

**새 화면을 만들지 않는다.** 계정 정보(로그인 이메일)·동기화 상태("● 동기화됨" / "○ 오프라인 · 온라인이 되면 이어서 보냅니다")·`[로그아웃]`·`[다른 기기 모두 로그아웃]`(확인 대화상자 동반, ADR-0020)은 **사이드바 하단 "계정 블록"**에 둔다 — app-shell.md R12 의 도구 줄(테마 토글 · 설정 · 백업/복원 · 루틴) 아래, 사이드바 맨 끝. 로그인 여부와 무관하게 늘 같은 자리인 도구 줄과 달리, 계정 블록은 세션에 종속된 상태라 나머지 진입점들과 분리해 맨 아래에 둔다(구조는 app-shell.md R12·§2-A 참조 — 이 스펙에서 다시 정하지 않는다). 사이드바 **맨 위**의 프로필 카드(이름·사진·한 줄 소개 — 세션 상태가 아니라 `Settings` 의 동기화되는 값)는 [profile.md](profile.md)·ADR-0023 이 정한다; 계정 블록과 섞지 않는다.

## 3. 규칙 (ADR-0015를 화면 규칙으로 구체화 — 번호는 ADR 섹션에 대응)

- R1. **로컬 표식**(`syncState.userSub` — 로그인 시 저장하는 비민감 플래그, 이메일 포함. 저장 위치는 §4)이 없으면 로그인 화면 외 **어떤 화면도 보여주지 않는다**. 표식이 있으면(오프라인 포함) 통과하고, 온라인이면 `/api/me` 로 세션을 확인한다(R6과 같은 판정, 아래 참고). 이 표식은 **인증이 아니라 표시용**이다 — 실제 인가는 매 요청마다 `HttpOnly` 세션 쿠키로 서버가 검사하고, 서버가 거부(401)하면 로그인 화면으로 돌아간다(로컬 변경은 아웃박스에 남아 같은 계정으로 재로그인하면 올라간다). 세션 쿠키는 `HttpOnly` 라 JS 가 읽을 수 없으므로, 오프라인 중에는 표식 하나로만 "로그인된 것처럼" 보여줄 수 있다는 뜻이다 — R6과 이 규칙이 예전에 서로 다른 판정 기준(쿠키 vs 표식)을 말해 모순으로 읽혔던 것을 여기서 하나로 합친다. **로그인 성공 시 `syncState.userSub` ≠ 응답 `sub`이면**(같은 브라우저에서 이전과 다른 구글 계정으로 로그인한 경우) 이전 계정의 로컬 데이터를 **자동으로 R7의 "내보내고 지우기" 경로**(내보내기 → 로컬 전량 삭제, `deviceId`는 유지)를 거친 뒤에만 새 계정으로 전량 풀을 받는다 — "올리기" 선택지는 주지 않는다(다른 계정의 로컬 데이터를 이 계정에 합치는 것은 항상 틀린 동작이므로). 이 표식·세션 값은 로그아웃·401 비인가·계정 전환 시 지운다(`deviceId`만 유지).
- R2. 로그인은 구글 OAuth 2.0 Authorization Code + PKCE 한 가지뿐이다(다른 로그인 수단 없음). 버튼 하나, 리다이렉트 후 자동으로 앱으로 복귀한다.
- R3. 서버(D1)가 단일 진실이고 IndexedDB는 캐시다(ADR-0015 §2) — **"기존" 화면·컴포넌트(로그인·동기화 붙이기 전부터 있던 코드)는 데이터 흐름이 바뀌지 않는다**: 여전히 `repositories` 인터페이스(ADR-0007)만 보고, 그 뒤에 어떤 구현체가 있는지 모른다. 이 스펙 자체가 만드는 **새 코드**(로그인 화면·첫 로그인 업로드 다이얼로그·동기화 상태 표시·`AuthGate`·사이드바 계정 블록)는 당연히 새로 생긴다 — "코드가 안 바뀐다"가 아니라 **"기존 코드의 데이터 흐름이 안 바뀐다"**가 불변식이다. 검증은 레이어 경계 lint + 계약 테스트(기존 `repositories` 인터페이스로 어떤 구현체를 넣어도 기존 화면이 동일하게 동작).
- R4. 충돌은 **레코드 단위 최신 우선**이고 판정 기준은 **ADR-0005 의 충돌 정책 그대로**다(`updatedAt` 큰 쪽이 이기고, 동률이면 서버 도착 순, 서버는 미래 시각을 수신 시각으로 클램프) — ADR-0005 를 supersede하지 않는다. 서버 `seq`(사용자별 단조 증가, 서버 `entities` 테이블의 로우별 컬럼)는 승패 판정 축이 **아니라** 델타 풀 커서이고, `updatedAt` 동률일 때만 타이브레이크로 쓴다(ADR-0015 §2). 사용자에게 병합 화면을 보여주지 않는다. **로컬에 아직 푸시하지 못한 변경**(아웃박스에 남아 있음)이 있는 상태에서 같은 로우가 풀로 들어오면: 이 기기에서 만든 뒤 한 번도 안 고쳤으면(`rev === 1`) 서버 로우를 받아들이고 아웃박스에서 뺀다, 이미 고쳤으면(`rev > 1`) 로컬을 지키고 이어지는 푸시가 나중 도착으로 서버에서 이긴다.
- R5. 다른 기기의 변경은 **즉시** 뜨지 않을 수 있다 — 앱이 앞으로 나올 때(`visibilitychange`·`focus`)·온라인 복귀할 때·보이는 동안 주기적으로 당겨온다(ADR-0015 §3, 간격은 구현 티켓에서 근거와 함께 정한다). 쓴 기기 자신은 낙관적 갱신으로 즉시 반영된다(오늘 MVP와 체감 동일).
- R6. 오프라인에서도 로컬 표식(R1)이 있으면 읽고 쓸 수 있다. 쓰기는 로컬에 쌓이고 온라인 복귀 시 올라간다. "저장됨"처럼 보이는데 서버에 아직 없는 상태를 **화면에 정직하게 표시한다**(사이드바 계정 블록의 동기화 상태, ADR-0015 §4).
- R7. 첫 로그인 시 로그인 전 로컬 데이터가 있으면 §2의 다이얼로그로 **올리기**/**내보내고 지우기**를 묻는다. **말없이 버리지 않는다**(ADR-0015 §5). "올리기"는 `enqueueAll()`(로컬 7테이블 전량을 아웃박스에 적재) + 정상 동기화 사이클로 구현한다 — backup.md의 가져오기 경로(`planImport`)는 재사용하지 않는다(T-94 구현 결정, 2026-09-21). 근거: R4의 서버 `updatedAt` LWW 판정이 곧 백업 병합(`planMerge`)의 newer-wins 규칙과 같아 **어느 경로를 타도 결과가 같고**, `enqueueAll` + 사이클 쪽이 기존 저장소 메서드·포트만 쓰는 코드 경로 하나로 끝난다(`SyncTransport`에 새 "전량 풀" 헬퍼를 추가하지 않아도 된다 — ADR-0018 포트 변경 없음). "가져오기 경로를 재사용한다"는 예전 문구는 이 문단으로 대체한다. **"내보내고 지우기" = 내보낸 뒤 이 기기에서 지운다**(backup R2 내보내기 → 로컬 전량 삭제): 올리지 않은 로컬 데이터를 그냥 두면 서버와 영영 동기화되지 않는 유령 상태로 남고, 이후 올릴 방법도 없다. 내보내기를 먼저 시키면 공용 PC에 흔적이 남지 않고, 나중에 다른 계정으로 로그인해도 이전에 두고 간 로컬 데이터와 섞이지 않으며, 파일로 남으니 "말없이 버리지 않는다"(ADR-0015 §5)도 지킨다. 이 파괴적 선택지는 §2 가 명시한 대로 app-shell.md **R14**를 따른다(비파괴 선택지가 초기 포커스).
- R8. 로그인 전 로컬 데이터가 없으면(첫 사용자) 다이얼로그 없이 바로 앱으로 들어간다.

## 4. 데이터

- 인증: Worker가 구글과 토큰을 교환하고(클라이언트 시크릿은 서버에만) 자체 세션을 `HttpOnly`·`Secure`·`SameSite=Lax` 쿠키로 발급한다. 브라우저는 구글 토큰을 저장하지 않는다. 사용자 식별자는 구글 `sub`(ADR-0015 §1). **세션은 로그인(기기)마다 하나이고, 같은 계정의 여러 기기가 동시에 로그인 상태일 수 있다** — 세션 전량 폐기는 재가입(계정 삭제 후 같은 계정으로 다시 로그인) 경로에서만 실행한다(ADR-0020, `worker/auth/session.ts#signIn`). 사용자가 직접 다른 기기 세션을 끊고 싶으면 `POST /auth/logout-others`("다른 기기 모두 로그아웃")를 쓴다.
- 저장소: 기존 `CategoryRepository`·`TodoRepository` 등 인터페이스는 그대로. 동기화 어댑터와 서버 순번(`seq`) 커서 기반의 풀/푸시가 신규(위치·구성은 ARCHITECTURE.md "클라우드 동기화" 행이 이미 지정해 두었다 — 이 스펙에서 다시 정하지 않는다). **클라이언트 `Meta`에는 필드를 더하지 않는다** — `Meta.rev`(ADR-0005, `touch` 마다 +1)는 그대로 둔다. **서버 `entities` 테이블에는 로우마다 사용자별 단조 증가 `seq` 컬럼을 둔다**(그 로우가 서버에 몇 번째로 도착했는지). 클라이언트는 그중 "마지막으로 받은 `seq`"만 **커서**로 하나 기억한다(ADR-0015 §2·§3 정정).
- 새 로컬 개념 넷의 정의와 위치:
  - `deviceId`: 이 브라우저 프로필을 가리키는 UUID. 최초 로그인 시 한 번 생성해 로그아웃·계정 전환에도 유지한다(다른 계정으로 전환해도 "같은 기기"라는 사실은 바뀌지 않으므로).
  - `syncOutbox`("아웃박스"): 서버에 아직 못 보낸 로컬 변경의 큐. `(tbl, id)` 유일(같은 로우를 여러 번 고쳐도 1건).
  - `syncState`: `deviceId`·`userSub`(R1의 로컬 표식)·풀 커서(`seq`)·`lastSyncedAt`을 담는 **새 IndexedDB 테이블**(단일 행). **`Settings`에는 넣지 않는다** — `Settings`는 동기화 대상 엔티티라(ARCHITECTURE.md §4) 넣으면 `userSub`·커서 같은 기기별 값이 다른 기기로 퍼진다. `userSub`·커서·`lastSyncedAt`은 로그아웃·401 비인가·계정 전환(R1) 시 지운다(`deviceId`는 유지).
  - "풀 커서": 위 `syncState`의 `seq` 필드 그 자체(별도 테이블이 아니다).
- 서버 쪽 D1 스키마(테이블·`seq` 컬럼)는 구현 티켓에서 정한다.

## 5. 접근성

- 로그인 버튼은 텍스트 라벨 동반("Google로 계속하기", 아이콘만 아님).
- 첫 로그인 업로드 다이얼로그는 app-shell 표준 다이얼로그 패턴(초기 포커스·`Esc`·포커스 복원) 재사용.
- 동기화 상태는 아이콘 + 텍스트 병기(색만으로 구분하지 않는다).

## 6. 범위 밖 (ADR-0015가 아직 정하지 않은 것 — 구현 티켓 또는 별도 ADR 필요)

- **선행 조건**: R2·§4 인증 관련 티켓은 사용자가 구글 OAuth 클라이언트 ID/시크릿과 Cloudflare D1 데이터베이스를 직접 발급하기 전까지 착수할 수 없다(ADR-0015 결과 4). `상태: approved`로 바뀌어도 이 선행 조건은 별개다 — 오케스트레이터는 자격증명 발급 여부를 먼저 확인하고 티켓을 발행한다.
- 데이터 내보내기(GDPR류)는 backup.md의 기존 내보내기로 갈음하고 이 스펙에서 새로 만들지 않는다. 세션 만료 정책의 구체값, R5 폴링 간격의 구체값은 범위 밖(구현 티켓에서 근거와 함께 정한다).
- 개인정보 처리방침(법적 의무 — ADR-0015가 "배포 전 필요"라고 명시하지만 이 스펙의 범위 밖).
- 실시간 푸시(WebSocket·Durable Objects) — ADR-0015가 의도적으로 뺐다(§재검토 트리거에 조건부로 남김).
- 구글 외 다른 로그인 수단, SNS 연동(Phase 3 `social.md`).

**예외(범위 안으로 당겨온 것)**

- **계정 삭제는 이번 범위에 포함한다**(`POST /api/account/delete` — users 행 삭제 → CASCADE로 세션·기기·데이터 삭제. 구현 티켓에서 확정).
- **계정 삭제 시 다른 기기의 처리 = 삭제 기록 + 안내 다이얼로그**(⑦-6 사용자 결정, 2026-09-21 구체화). 서버에 `users`와 별도로 — CASCADE 체인 밖에 — **삭제된 사용자 기록**(`deleted_users` 성격의 테이블, `sub`·`deletedAt`)을 둔다. 로그인돼 있던 **다른 기기**가 다음 동기화/세션 확인에서 이 상태를 만나면 **조용히 로그아웃시키지 않고** "이 계정은 삭제되었습니다" 안내를 띄운 뒤, **R7의 "내보내고 지우기"**(로컬 데이터 내보내기 → 로컬 전량 삭제, backup R2 재사용)를 탄다 — 로그아웃 결정("내보낸 뒤 삭제")과 **같은 원칙**(ADR-0015 §5 "말없이 버리지 않는다")이다. 자동으로 말없이 지우지 **않는다**(그 기기에만 있던 미동기화 데이터를 건질 기회를 준다).
  - **왜 이 대안인가(기각한 대안 둘)**: (a) _단순 401 로그인 화면_(세션만 지우고 특별 처리 없음) — 구현은 가장 간단하지만 "세션 만료"와 "계정 삭제"를 화면에서 구분하지 못한다. **결정적 함정**: 같은 구글 계정으로 다시 로그인하면 OAuth 콜백의 `users` upsert가 그 `sub`로 새 행을 만들어 **계정이 되살아난다** — "삭제했는데 왜 살아있지"가 된다. `deleted_users` 기록이 있으면 이 재가입을 콜백 시점에 걸러낼 수 있다(정확한 차단 지점은 T-93에서 확정). **정정(ADR-0020, 2026-09-21)**: 그 차단 지점은 `worker/auth/session.ts#signIn` 하나이고, 세션 전량 폐기는 `deleted_users` 존재로 조건화돼 있다 — 재가입이 아닌 평범한 로그인은 같은 계정의 다른 기기 세션을 건드리지 않는다(다기기 동시 로그인이 정상 동작이다). (b) _자동(말없이) wipe_ — 그 기기에만 있던, 아직 안 올라간 아웃박스 변경을 사용자 모르게 날려 ADR-0015 §5 "말없이 버리지 않는다"를 정면으로 어긴다.
  - **D1 스키마 영향(중요)**: D1은 나중에 테이블을 더하기는 되지만 이미 나간 마이그레이션을 고치긴 어렵다 — `deleted_users`는 **T-93의 첫 마이그레이션(`0001_init.sql`)부터** 넣는다. 나중 마이그레이션으로 미루지 않는다.
  - **미정(T-93에서 확정)**: 다른 기기가 이 상태를 정확히 어떤 응답으로 "만나는지"의 배선. `users` 삭제가 `sessions`까지 CASCADE로 즉시 지우면 다른 기기의 다음 요청은 sub를 알 수 없는 평범한 401이 될 수 있다 — `deleted_users` 조회가 가능하려면 세션 삭제 타이밍·방식(즉시 CASCADE vs 지연)을 함께 설계해야 한다. 이 구체 메커니즘(엔드포인트·응답 코드·세션 정리 시점)은 이 스펙의 범위 밖이고 T-93이 정한다 — 이 문서가 고정하는 것은 **제품 동작**(안내 다이얼로그 + R7 재사용, 자동 wipe 금지)과 **삭제 기록 테이블이 첫 스키마에 있어야 한다는 것**뿐이다.
- **이 기기에서 스스로 계정을 삭제할 때(계정 블록의 `[계정 삭제]`)도 내보내기는 필수다**(T-94 구현 결정, 2026-09-21 — "제안"이 아니다). 확인 → **내보내기**(성공해야 다음 단계로) → 서버 `deleteAccount` → `wipeLocal`. 근거: 계정 삭제는 되돌릴 수 없고, 로그아웃(위 항목)·R7·§6의 다른 기기 안내가 전부 "내보내야만 지운다"는 같은 원칙(ADR-0015 §5 "말없이 버리지 않는다")을 따르는데 자기 자신의 계정 삭제만 예외로 둘 이유가 없다 — 오히려 가장 파괴적인 동작이라 더 엄격해야 한다.
- **로그아웃 시 로컬 IndexedDB 캐시를 지운다** — R7·R1과 같은 이유(공용 PC 흔적 방지, 계정 전환 시 미혼입)로 R7의 "내보내고 지우기" 경로를 재사용한다(⑦ 사용자 결정).
- backup.md **R7-a**(로그인 상태에서 백업 "교체" 모드 비활성화)는 이 스펙 R3·R4가 만드는 상황(서버가 진실, 물리 삭제가 툼스톤 없이 되돌아옴)의 직접적 귀결이다 — backup.md에서 규칙을 정하고 여기서는 역참조만 한다.
- 로그인 필수 이후 **`Settings`가 동기화 대상이 되면서** `lastBackupAt`(backup R10)이 기기 간에 퍼진다 — 다른 기기의 내보내기가 이 기기의 백업 경고 점을 끈다. 막지 않고 감수한다(후속 ADR에서 정리할 사항으로 남긴다).
