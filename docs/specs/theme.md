# 테마·컬러 시스템 스펙

- 상태: implemented · 관련 ADR: ADR-0003 · 리서치 참조: reference-app-research.md §6 전체(추정치를 아래 확정값으로 대체), §9 과제 2

## 1. 목표

레퍼런스 앱의 감성(파스텔·화이트 베이스, 큰 라운드, 넉넉한 여백, 카테고리 색으로 꾸미는 재미)을 **수치로 고정**해 어떤 에이전트가 만들어도 같은 룩이 나오게 한다. 라이트/다크와 강조색은 사용자가 고르고, 나머지는 토큰이 정한다.

## 2. 화면과 인터랙션

```
 사이드바 하단:  [☾ 다크]  [⚙]           ⚙ 팝오버(240px):
                                          ┌ 테마 ───────────────────┐
                                          │ (●) 시스템 ( ) 라이트 ( ) 다크 │
                                          │ 강조색                    │
                                          │  ●  ●  ●  ●  ●  ●         │  ← 12색(§3-C와 동일), 28px, 선택 시 체크
                                          │  ●  ◉  ●  ●  ●  ●         │
                                          └───────────────────────────┘
```

- `☾` 버튼: 라이트 ↔ 다크 즉시 토글(시스템 모드였다면 명시 모드로 전환). 팝오버: 3모드 + 강조색.
- 강조색 변경은 즉시 전체 반영(선택 날짜 셀, 링, 버튼, 포커스 외곽 제외). 좁은 화면: 동일 팝오버(드로어 안).
- 상태: 로딩 없음(첫 페인트 전에 적용, R6). 에러: 저장 실패 시 화면은 바뀐 채 토스트, 새로고침 시 이전 값.

- R5. `prefers-reduced-motion: reduce`에서 모든 `--motion-*`는 0ms.
- R21. **고도는 알파가 아니라 퍼짐으로 만든다.** `--elev-sm` 이 한 겹(`0 1px 2px / .06`)이던 동안 찍힌 픽셀은 **2px 띠 · 1.102:1**(다크 1px · 1.042:1)이어서, 같은 카드의 1px 보더(**1.192:1**)보다 약했다 — 카드를 카드로 보이게 하던 것이 고도가 아니라 보더였다(T-63 실측). 이 앱에서 실제로 떠 보이는 면(커맨드 팔레트·토스트)이 쓰는 `--elev-md` 는 알파가 `.08` 뿐인데도 **22px** 을 퍼뜨린다. 그러므로 어두워서가 아니라 **넓어서** 뜬다. 그림자를 진하게 만들어 부유감을 얻으려 하지 않는다 — 파스텔·저채도 정체성(리서치 §6)이 깨진다. 지금 값의 실측은 라이트 **13px 띠 · 1.218:1**(가장 어두운 픽셀 `rgb(228,228,230)`)이다.
- R22. **다크에서 카드의 경계는 그림자가 아니라 보더가 진다.** 다크 캔버스(`#141418`) 아래 그림자의 **천장은 1.136:1** 이다 — 알파를 1(순수 검정)로 깔아도 그보다 어두워지지 않는다(T-63 실측). 반면 다크 보더(`#2e2e38`)는 캔버스 대비 **1.368:1** 로 라이트 보더(1.192:1)보다 이미 세다. 따라서 다크에서 `--elev-sm` 의 알파를 더 올리지 않는다(얻는 것은 ≤0.06 인데 검은 무리만 생긴다). 라이트와 **같은 기하**에 비례한 알파(`.30`/`.36`)만 주어 접촉감을 남기고(실측 7px · 1.076:1), 경계는 보더에 맡긴다. 다크의 대비가 라이트보다 낮다는 것은 결함이 아니라 **매질의 한계**다.
- R30. **모바일 전역 글자 축소(calendar-layout.md R11 개정 — 사용자 결정, 2026-09-22).** 앞선 단위(calendar-layout.md WU)는 "달력만 줄이고 전역은 보류"했으나, 사용자가 "글자 크기도 전체적으로 줄여도 될 것 같다" 고 직접 밝혀 전역으로 넓혔다. `@media (max-width: 767.98px)` 에서 `--text-sm`~`--text-3xl` 를 위 표의 값으로 낮춘다. `--text-xs`(12)는 본문 판독성 하한이라 그대로 둔다. **터치 치수(`--control-height` 36 · `--control-hit-min` 32 · 체크박스 22px)는 이 축소와 무관하다** — 글자만 줄고 클릭 영역은 WCAG 2.5.8 최소(24×24)를 그대로 넘는다. 달력 전용 `--cal-day-text`(밀도 표, calendar-layout.md §2 R12)는 원래 `var(--text-base)` 를 참조했지만, 전역 축소로 `--text-base` 자체가 14→13 이 되면 달력 글자가 다시 얹혀 이중으로 작아지므로 `tokens.css` 에서 리터럴 `14px` 로 떼어 놓았다 — 달력은 별도 단위에서 이미 실측을 마쳤고(calendar-layout.md R9) 더 줄이지 않는다.
- R31. **브레이크포인트 단일화.** Tailwind 기본 `--breakpoint-md`(`48rem`)는 브라우저 루트 글꼴 크기가 16px 가 아니면(사용자가 접근성 설정으로 키우거나 줄인 경우) 768px 지점에서 어긋난다 — CSS 미디어 쿼리(`max-width: 767.98px`, px 고정)·JS `SHELL_BREAKPOINTS.narrow`(768)는 그 설정과 무관하게 항상 768px 이라 셋이 갈라질 수 있었다. `tokens.css` 의 `@theme` 에 `--breakpoint-md: 768px` 를 px 로 다시 선언해 세 곳을 한 지점으로 고정한다. 이 레포가 실제로 쓰는 다른 브레이크포인트는 `sm:`(640px, `ShellHeader`·`CommandPalette`·`DateStripHeader`·`ReportsScreen`) 뿐인데, 대응하는 JS 상수가 없어 그대로 둔다 — `lg:`·`xl:`·`2xl:` 는 이 레포 어디서도 쓰지 않아 손대지 않는다.
- R23. **고도 사다리는 모든 지점에서 단조다.** 높은 단은 낮은 단보다 어느 픽셀에서도 밝아서는 안 된다. `--elev-md` 가 퍼짐 한 겹(`0 6px 20px`)뿐이던 동안에는 접촉 겹이 `--elev-sm` 에만 있어서, 면 바로 아래 픽셀이 **sm `rgb(228,228,230)` vs md `rgb(236,236,238)`** 로 **낮은 단이 더 진했다**(T-66 실측, 같은 배경·같은 기하의 쌍둥이 면). 퍼짐이 크게 벌어진 화면에서는 안 보이지만, 두 단을 가까이 놓는 순간(카드 위 팝오버) 드러난다 — 토큰은 쓰일 자리를 고르지 않으므로 사다리 자체가 안전해야 한다. 해법은 **알파가 아니라 기하**다(R21): md 에 sm 과 **같은 알파**(`.05`/다크 `.30`)의 접촉 겹을 주되 오프셋·흐림을 같은 배율로 두 배(`1px 2px` → `2px 4px`)로 눕힌다. 오프셋/흐림 비가 같으면 접촉 지점에서 최소한 같고 그 아래로는 항상 더 넓게 남는다. 실측: 면 아래 14개 표본 전부에서 md ≤ sm(밝기) — 라이트 md 가장 어두운 픽셀 `rgb(227,227,229)`·`1.229:1`(sm `1.218:1`), 다크 md `1.077:1`(sm `1.076:1`, 천장 1.136 — R22). 고쳐도 팔레트·토스트는 **더** 떠 보인다(팔레트 라이트 `1.125 → 1.207:1`, 다크 `1.267 → 1.404:1`).

### 3-E. 모드·저장·적용

- R6. 테마 모드 ∈ `system | light | dark`, 기본 `system`. 적용은 `<html data-theme="light|dark">`. 첫 페인트 전에 적용되어 깜빡임이 없어야 한다(저장소가 비동기이므로 localStorage 미러 `tasky.theme.v1`을 첫 페인트 전 스크립트가 읽는다).
- R7. `system` 모드는 OS 변경(`prefers-color-scheme`)을 실시간 따른다.
- R8. 테마·강조색은 저장소 `Settings`에 저장되며 백업에 포함된다. localStorage 미러는 캐시일 뿐이며, 저장소 값이 우선한다.
- R29. **목록 행 hover 는 행 전체를 `--color-surface-3` 으로 칠하고, 그 행의 `--color-muted` 글자는 `--color-text` 로 같이 진해진다.** 둘은 한 덩어리이지 취향이 아니다 — `--color-muted` 는 `--color-surface-2` 위에서 이미 **4.48:1**(실측)로 R9 의 4.5:1 경계에 걸쳐 있어서, 배경만 더 진하게 하면 `#E9E9F0` 기준 **4.11:1** 로 떨어진다. 글자를 함께 올리면 11.62:1 이 되어 여유가 생긴다. 행 안의 개별 컨트롤(드래그 손잡이·`⋯`)은 이 행에서 자기 배경 hover 를 쓰지 않는다 — 더 진한 띠 위에 `--color-surface-2` 조각이 얹히면 **더 밝은** 얼룩이 된다. 포커스 링은 그대로다(키보드 경로는 이 규칙과 무관).
- R9. 대비(배경 `--color-bg`/`--color-surface` 기준): 본문·보조 텍스트 ≥ 4.5:1. 비텍스트는 WCAG 2.1 SC 1.4.11 의 범위 그대로 — **컨트롤·상태를 식별하는 데 필요한** 시각 요소(포커스 링, 미체크 체크박스 테두리, 의미를 가진 아이콘)만 ≥ 3:1이고, **순수 장식 경계선·구분선은 대상이 아니다**. 그래서 `--color-border`(라이트 1.24 / 다크 1.26)와 `--color-faint`(1.97 / 2.49)는 카드·패널 윤곽과 비활성 표시에만 쓰며 3:1 을 요구하지 않는다(그 선이 사라져도 컨트롤을 식별할 수 있다). 테두리가 컨트롤의 유일한 식별 수단인 곳에는 3:1 을 넘는 색을 쓴다(`--color-muted` 4.76 / 6.54). `--color-danger`(라이트 3.59 / 다크 6.61)는 3:1 은 넘고 4.5:1 에는 못 미치므로 **파괴 버튼 배경·아이콘·테두리 전용**이고 본문 글자색으로 쓰지 않는다 — 그 위 글자는 `--color-on-accent`(4.56 / 6.38). 카테고리 색은 배경·점·막대에만 쓰고 글자색으로 쓰지 않는다.

### 3-G. "선택됨" 표현 — 파스텔 채움 + 잉크 링 (앱 전체 규정)

라이트에서 **12 프리셋이 전부 배경과 3:1 에 못 미친다**(측정: `--color-accent` vs `--color-bg` / `--color-surface`).
다크는 전부 여유가 있다. 채도·명도를 올려 채움만으로 3:1 을 맞추면 §1 의 파스텔 정체성이 깨지므로,
**채움은 파스텔로 두고 WCAG 2.2 SC 1.4.11 의 3:1 은 잉크 링이 진다.**

| 프리셋(라이트 채움 vs `--color-bg` / 다크 채움 vs `--color-bg`)                         | 라이트 | 다크   |
| --------------------------------------------------------------------------------------- | ------ | ------ |
| `coral` 2.07 · `peach` 1.67 · `orange` 1.45 · `yellow` 1.14 · `lime` 1.26 · `mint` 1.38 | 전부 ✗ | 전부 ✓ |
| `teal` 1.51 · `sky` 1.77 · `blue` 1.90 · `lavender` 2.05 · `lilac` 1.69 · `gray` 1.54   | 전부 ✗ | 전부 ✓ |
| 다크 값 범위: 6.33–11.55(`--color-bg` 기준) · 5.84–10.66(`--color-surface` 기준)        | —      | ✓      |

| 토큰                      | 값                    | 용도                                                        |
| ------------------------- | --------------------- | ----------------------------------------------------------- |
| `--color-selected`        | = `--color-accent`    | 선택 채움(파스텔 — 라이트/다크 모두 프리셋 값 그대로)       |
| `--color-on-selected`     | = `--color-on-accent` | 채움 위 글자(모든 프리셋에서 ≥ 4.5:1)                       |
| `--color-selected-ring`   | = `--color-text`      | 선택 경계선 — **3:1 을 지는 선**(라이트 13.47 / 다크 15.75) |
| `--control-selected-ring` | `2px`                 | 링 두께(미체크 체크박스·스와치 테두리와 같은 굵기)          |

- R17. **선택 상태를 배경 채움으로 표시하는 컴포넌트는 채움과 링을 함께 쓴다** — `--color-selected` 채움 + `--control-selected-ring` 두께의 `--color-selected-ring` 링(안쪽 링 권장: 크기가 변하지 않는다). 채움만 쓰는 선택 표시는 리뷰 **Blocker** 다(라이트에서 1.4.11 미달).
- R18. 링 색은 **강조색에서 파생하지 않는다.** 파스텔을 3:1 까지 어둡게 만든 파생색은 더 이상 파스텔이 아니다. 링은 항상 중립 잉크(`--color-text`)이며, 프리셋이 바뀌어도 링은 그대로다.
- R19. **채움 없이 표식(✓·굵은 테두리)만으로 선택을 말하는 표현도 같은 링 토큰을 쓴다** — 강조색·카테고리 색 스와치가 그렇다(채움은 색 견본 자체라 강조색이 아니다). 결과적으로 앱의 "선택됨" 은 **어디서나 `--color-selected-ring` 2px 잉크 선**이라는 한 가지 언어다(FEEL_REPORT §7-H(1) 의 분기 해소).
- R20. "오늘"(날짜 스트립 R3)처럼 **선택이 아닌** 표시는 계속 강조색 링을 쓴다 — 잉크 링은 "선택됨" 전용이라 둘이 겹치지 않는다. 선택이면서 오늘이면 잉크 링이 이긴다.

> **트레이드오프(숨기지 않는다).** 이 규칙은 접근성을 위해 선택 칸에 **잉크 선 하나를 더 그린다** — 채움만 있던 때보다 화면이 미세하게 또렷해지고, 순수한 "파스텔 덩어리" 느낌은 조금 줄어든다. 대신 12 프리셋의 **색 값은 하나도 바꾸지 않아** 파스텔 정체성의 본체(색 자체)는 그대로 남는다. 반대 선택지였던 ① 프리셋을 어둡게(정체성 파괴, 12색 재설계) ② 선택 전용 진한 파생색 12종 추가(팔레트 2배 + 어두운 칸) ③ 페이지 배경을 어둡게(라이트 테마 전체가 회색으로) 는 전부 색 자체를 건드린다. 선(2px)은 면(56×72px)보다 정체성을 덜 건드린다는 판단이다.

### 3-H. 데이터 표현 색 — 히트맵 진하기(5단계, stats.md R6)

데이터를 그리는 색은 **세 축**이고 축마다 소스가 다르다. **정체성**(어느 카테고리인가)은 `--cat-color`(§3-C, 런타임 값)만, **상태**(위험·요일)는 §3-A 의 의미 토큰만, **양**(얼마나 했나)은 이 절의 **잉크 명도 램프**만 쓴다. 양을 유채색으로 그리지 않는다 — 12 프리셋이 hue 원을 덮고 있어(가장 넓은 빈 구역 59°, 어떤 hue 든 프리셋과 ≤ 30°) 유채 램프의 밝은 단계는 반드시 누군가의 카테고리 색(기본 강조색 `sky` 포함)과 겹친다. 색각이상 시뮬에서는 12색 중 3~~5색이 채도 0.04 아래의 **밝은 회색**(라이트 L 0.72~~0.94 · 다크 0.64~0.85)으로 무너지므로 그 명도 대역에 데이터 단계를 두면 hue 와 무관하게 겹친다.

stats.md R6 의 활동 히트맵이 쓰는 칸 진하기 토큰. "기록 없음"(그날 투두 0개) 1단계 + 완료율 4단계(0% · 1~~49% · 50~~99% · 100%) = 총 5단계다.

| 토큰                | 의미                          | 라이트    | 다크      |
| ------------------- | ----------------------------- | --------- | --------- |
| `--color-heatmap-0` | 기록 없음(그날 투두 0개)      | `#E7E7F0` | `#28282F` |
| `--color-heatmap-1` | 0% 완료(투두는 있으나 미완료) | `#73747B` | `#43434A` |
| `--color-heatmap-2` | 1~49% 완료                    | `#5A5A61` | `#5D5D64` |
| `--color-heatmap-3` | 50~99% 완료                   | `#414249` | `#787880` |
| `--color-heatmap-4` | 100% 완료                     | `#2B2B33` | `#EDEDF2` |

- R24. **양은 잉크로 그린다.** 히트맵 5단계는 `--color-text` 의 hue(285°)·채도(≤ 0.014)를 가진 **무채색 명도 램프**이고, 4단계(100%)는 두 모드 모두 `--color-text` 와 같은 값이다("100% 는 잉크로 꽉 찬 칸"). 0단계(기록 없음)는 `--color-border` 톤이다(빈 칸은 경계선이지 데이터가 아니다). 값은 사용자가 고르는 `--color-accent`(§3-B)를 따라가지 않는 **고정 HEX** 다 — R18 과 같은 이유로, 파스텔을 진하게 만든 파생색은 파스텔이 아니며 이 앱에서 파스텔 밖으로 나가는 색의 언어는 잉크다(`--color-selected-ring = --color-text`). 강조색을 바꿔도 "많이 완료했다"는 의미가 흔들리지 않고, 카테고리 12색(전부 유채, `gray` 만 C 0.014)과는 **종류**가 다르다. 이름은 `--color-` 접두 + `0~4` 인덱스이고 `@theme` 안에 둔다(런타임 데이터가 없는 고정값 — src/styles/AGENTS.md 규칙 3).
- R25. **실측(단조·인접·색각이상).** 세 면(`--color-bg`·`--color-surface`·`--color-surface-2`) 모두에서 0→4 대비가 단조 증가한다 — 라이트(bg 기준) `1.18 → 4.46 → 6.56 → 9.59 → 13.47`, 다크 `1.26 → 1.87 → 2.81 → 4.20 → 15.75`. 라이트는 진할수록 어둡고 다크는 진할수록 밝다(R22 와 같은 매질의 이유). 인접 단계 대비는 정상 시각 라이트 ≥ 1.40 · 다크 ≥ 1.49 이고, 색각이상 3종(protan·deutan·tritan, Viénot 1999·Machado 2009 두 모델) 시뮬에서도 라이트 ≥ 1.38 · 다크 ≥ 1.47 이다 — 무채색이라 시뮬이 값을 거의 바꾸지 못한다. 0→1 만 큰 도약(라이트 3.79)인 것은 의도다: "기록 없음"과 "0%" 는 이웃 눈금이 아니라 종류가 다른 칸이다. 트레이드오프: 라이트 1단계가 4.46:1 로 진하다. 더 밝게(L 0.71, 2.5:1) 두면 protan 시뮬에서 `coral` 이 같은 명도의 회색으로 무너져 ΔE 1.2 로 겹친다(실측) — 데이터 단계는 라이트 OKLCH L ≤ 0.56 이어야 하고 그 진하기는 색각이상 대가다.
- R26. **데이터 표현 색은 12 프리셋 전부와 재고 나서 들어온다.** 이 절에 값을 더하거나 바꿀 때는 같은 모드의 12색(라이트는 라이트 값, 다크는 다크 값 — R3 로 강조색과 같은 집합) 전부와 WCAG 대비·OKLab ΔE 를 계산해 가장 가까운 색과 값을 이 절에 적는다. 히트맵 단계 1~~4 의 현재 값: 라이트 최소 CR 2.15(`coral`)·ΔE 22.8(`lavender`), 다크 최소 CR 1.36(`yellow`)·ΔE 13.4(`gray`), `sky` 와는 라이트 2.52 / 다크 1.83. 남는 잔여도 적는다 — 다크 3단계 vs `gray` 다크 ΔE 13.4(0단계가 카드에서 보여야 하고 인접이 1.46 이상이어야 해서 3단계가 L 0.575 아래로 못 내려간다), 다크 3단계 vs `coral` 다크 protan 시뮬 ΔE 6.9(시뮬 대비 1.32 — 다크 파스텔이 protan 에서 L 0.64~~0.83 회색으로 무너지는 대역 바로 아래). 그래서 색만으로 정체성을 말하지 않는다는 stats.md §5(막대 = 이름 라벨 + `progressbar`, 히트맵 = `role=img` + 대체 `table`)가 이 절의 전제다. 다음 양 표현(추이 막대 등)은 새 램프를 만들지 않고 이 토큰을 쓴다.
- R27. **`forced-colors`(Windows 고대비 등)에서 진하기는 무효화된다.** UA 가 `background-color` 를 시스템 색 하나로 통일해(`DateCell.tsx`·`CommandPaletteList.tsx` 의 `forced-colors:` 분기가 같은 제약을 겪는다) 칸 5단계가 색만으로는 0 bit 를 전달한다 — 히트맵 칸에 `forced-colors:` 전용 무늬·텍스트를 새로 그리지 않는다. 대신 칸은 색이 아닌 채널로 읽힌다: R26 이 전제하는 stats.md §5 의 숨긴 대체 `table`(칸별 날짜·완료율 텍스트)이 이미 그 채널이고, 그 모드에서도 그대로 유효하다. T-85 는 이 문장을 구현 시점에 다시 발명하지 않는다. 단, 칸이 격자로 보이게 하는 **레벨과 무관한 균일한** 테두리는 이 금지의 대상이 아니다 — 5단계를 구분하는 차등(레벨별 굵기·무늬)만 금지다.
- R28. **히트맵 격자는 `--color-surface` 위에 둔다.** R25 의 대비 실측은 세 면 모두에서 단조 증가를 보장하지만 절댓값은 면마다 다르다(실측: 다크 0단계가 `--color-surface` 기준 1.16 인데 `--color-surface-2` 기준 1.03 으로 사실상 사라진다) — R26 이 "카드에서 보여야 한다"고만 못박고 어느 면인지는 정하지 않은 빈틈이다. 히트맵을 그리는 컴포넌트는 격자 자신의 배경을 `--color-surface` 로 스스로 선언한다(부모 카드가 우연히 같은 색이어서가 아니라). 중첩된 카드 안에 들어가 배경이 `--color-surface-2` 가 되는 배치를 두지 않는다.

## 4. 데이터

- domain `Settings = Meta & { id: 'default', theme, accentColor, seededAt?, lastBackupAt? }` — `Meta`(`createdAt`·`updatedAt`·`rev`·`deletedAt?`)를 공통으로 갖는다(ADR-0005. 단일 행이라 `deletedAt`은 설정되지 않는다). 팔레트 프리셋(§3-C)은 도메인 상수 + 조회 함수(HEX → 프리셋, 프리셋 → 다크 값).
- 레포지토리: `SettingsRepository.get()`(없으면 `undefined` — 기본값은 도메인 `createSettings(deps)`가 만들고 `upsert` 한다), `upsert(Persistable<Settings>)`. 레포지토리는 시각·`rev`를 만들지 않는다(ADR-0005·0007).

## 5. 접근성

- `☾` 버튼 `aria-label="다크 모드로 전환"`/`"라이트 모드로 전환"` + `aria-pressed`.
- 팝오버: 모드는 `radiogroup`, 강조색은 `radiogroup`(이름 = 색 이름). `Esc` 닫기, 포커스 복귀.
- 포커스 링은 `--color-focus` 2px + 오프셋 2px, 절대 제거하지 않는다.

## 6. 범위 밖

- 커스텀 HEX(1.5), 폰트 선택, 고대비 테마, 배경 이미지·스티커·마스코트, 카테고리별 아이콘 세트.
