# 데이터 백업/복원 스펙

- 상태: approved · 관련 ADR: ADR-0002, ADR-0009(`DatasetRepository`·`adopt`·물리 삭제 예외) · 리서치 참조: reference-app-research.md §4(백업/동기화가 로그인 기반), §9 과제 4

## 1. 목표

계정이 없으므로 **내 데이터를 파일로 갖는 것**이 유일한 안전망이다. 클릭 두 번으로 JSON 하나를 받고, 다른 브라우저·기기에서 같은 파일로 되살린다. 실수로 지운 뒤에도 옛 백업을 "병합"하면 최신 상태를 해치지 않고 빈 곳만 채워진다.

## 2. 화면과 인터랙션

```
 사이드바 하단 "⇅ 백업/복원" → 다이얼로그(480px, 좁은 화면 전폭 시트)
 ┌ 백업/복원 ─────────────────────────────── ✕ ┐
 │ 내보내기                                     │
 │  카테고리 4개 · 할 일 312개                   │
 │  마지막 백업: 2026-09-01 (14일 전)   [JSON 내보내기] │
 │──────────────────────────────────────────────│
 │ 가져오기                                     │
 │  [파일 선택…] tasky-backup-2026-09-01.json    │
 │  (●) 병합 — 같은 항목은 더 최근 것을 남겨요     │
 │  ( ) 교체 — 지금 데이터를 모두 지우고 파일로 바꿔요│
 │      [ ] 지금 데이터가 사라지는 것을 이해했어요  │  ← 교체 선택 시에만 표시·필수
 │                              [취소] [가져오기] │
 └──────────────────────────────────────────────┘
 결과 토스트: "카테고리 4개, 할 일 312개를 가져왔어요 (추가 20 · 갱신 3 · 유지 289)"
 경고 점: 사이드바 "백업/복원"에 작은 점 — 마지막 백업 30일 초과(또는 없음) 이면서 투두 ≥ 20개일 때
              (닫기 버튼 없음 · 끄는 설정 없음 — R14. 저장을 확인 못 한 백업은 임계가 절반)
```

- 상태: **빈 상태** 데이터 0개면 내보내기 버튼 비활성 + "아직 내보낼 데이터가 없어요". **로딩** 가져오기 진행 중 버튼 스피너 + 다이얼로그 닫기 불가. **에러** 형식 오류 → 파일 아래 `role=alert` 문구(§3 R8), 저장 실패 → "가져오지 못했어요. 파일은 바뀌지 않았어요" (교체 모드는 전부 롤백).

## 3. 규칙

- R1. 내보내기 파일명 `tasky-backup-YYYY-MM-DD.json`(로컬 날짜), MIME `application/json`, UTF-8, 들여쓰기 2칸.
- R2. 파일 형식:
  ```json
  {
    "app": "tasky",
    "schemaVersion": 1,
    "exportedAt": "2026-09-15T09:00:00.000Z",
    "settings": { "theme": "system", "accentColor": "#7CC6FF", "updatedAt": "2026-09-15T08:59:00.000Z" },
    "categories": [/* 삭제되지 않은 것 + 아래 todos/focusSessions가 가리키는 tombstone(deletedAt 유지) */],
    "todos": [/* Todo 전체 필드, deletedAt 있는 것 제외 */],
    "focusSessions": [/* FocusSession 전체 필드, timer.md */]
  }
  ```
- R3. `schemaVersion`은 저장소 스키마 버전(TECH_PLAN §5)과 같다. 파일 버전 < 현재면 가져오기 전에 순차 변환, 파일 버전 > 현재면 거부("더 새로운 버전의 Tasky에서 만든 파일이에요").
- R4. 검증: `app === "tasky"`, 배열 타입, 각 항목 필수 필드·타입, 카테고리 이름/색/투두 제목 길이(각 스펙 규칙), 투두의 `categoryId`가 파일 안 카테고리(tombstone 포함)에 존재, 세션의 `todoId`는 없어도 됨(없으면 `null`로 정규화). 하나라도 실패하면 아무것도 쓰지 않는다.
- R5. 알 수 없는 필드는 무시하고 보존하지 않는다(경고 없음).
- R6. **병합**(카테고리·투두·세션 공통): 비교 대상인 "현재 데이터"는 **툼스톤을 포함한 전량**(`DatasetRepository.readAll()`)이다 — 엔티티 조회로 만들면 로컬에서 지운 항목이 "로컬에 없음"으로 보여 파일의 옛 비삭제 버전이 부활하고, 적용 시 그 툼스톤이 영구 소실된다(§4). `id`가 같으면 `updatedAt`이 더 최근인 쪽을 남긴다(같으면 현재 데이터 유지). 소프트 삭제 상태도 같은 규칙(tombstone이 더 최근이면 삭제 유지)이며, **남기기로 한 툼스톤은 결과 스냅샷에 그대로 실린다**(빼면 삭제가 취소된 것과 같다). 파일에만 있는 항목은 추가. 설정은 파일 쪽이 더 최근일 때만 갱신. 파일에 `running/paused` 세션이 있으면 `canceled`로 바꿔 넣는다(실행 중 세션은 1개, timer R5). 가져온 항목의 공통 필드(`createdAt`·`updatedAt`·`rev`·`deletedAt`)는 **파일 값 그대로** 들어간다 — 여기서 시각을 새로 찍으면 R6의 비교 기준과 R2 왕복 동일성이 무너진다.
- R7. **교체**: 현재 카테고리·투두·세션을 전부 지우고(물리 삭제 — 근거는 ADR-0009 결정 4, 확인 체크박스는 거기에 더해지는 안전장치다) 파일 내용으로 채운 뒤 설정 갱신. **단일 트랜잭션, 실패 시 전부 롤백.** 확인 체크박스 필수. 병합도 같은 적용 경로를 쓰므로(§4) 어느 모드에서도 "카테고리는 들어갔는데 투두는 안 들어간" 중간 상태가 생기지 않는다.
- R7-a. **로그인(동기화 켜짐) 상태에서는 교체 모드를 비활성화한다**(병합만 가능). 교체는 로컬을 물리 삭제하는데 툼스톤이 없어, 파일에 없던 로우가 서버에는 남아 있다면 다음 풀에서 그대로 되돌아와 교체가 "안 먹는" 것처럼 보인다(sync.md와 상충). 다이얼로그에서 "( ) 교체"를 `aria-disabled` + 이유 툴팁("로그인 상태에서는 병합만 가능해요")으로 보여준다 — 옵션을 숨기지 않고 왜 못 쓰는지 알려준다.
- R8. 형식 오류 문구: JSON 파싱 실패 "JSON 파일이 아니에요", `app` 불일치 "Tasky 백업 파일이 아니에요", 검증 실패 "파일 내용이 올바르지 않아요 (todos[12].title)"(첫 오류 경로 표시).
- R9. 파일 크기 ≤ 20MB. 초과 시 읽지 않고 "20MB 이하 파일만 가져올 수 있어요".
- R10. 내보내기 성공 시 `Settings.lastBackupAt` 갱신. 다이얼로그와 경고 점은 이 값을 사용. **그와 함께 "이 기기가 저장 완료를 관측했는가"(확인/미확인)를 기록한다** — 브라우저가 저장 성공을 알려주는 경로(File System Access API)로 썼을 때만 "확인"이고, 앵커 내려받기는 취소·차단을 알 방법이 없으므로 "미확인"이다. 이 비트는 **기기별**로 둔다(백업 파일에 실려 다른 기기로 건너가면 보지도 않은 저장을 확인했다고 말하게 된다 — R2는 `settings`를 통째로 내보낸다). 판정은 R14.
- R11. 가져오기 완료 후 선택 날짜의 목록·주 요약·카테고리·달성률을 다시 조회한다. 페이지 새로고침 불필요.
- R12. 병합·교체 결과 토스트에 추가/갱신/유지 개수를 표시한다(R6·R7 계산 결과).
- R13. 1,000개 카테고리·50,000개 투두 파일(≈15MB) 가져오기가 10초 안에 끝나고 UI가 멈추지 않는다(청크 500개 단위 쓰기).
- R14. **경고 점은 끌 수 없다.** 닫기(✕)도 "다시 보지 않기" 설정도 없고, 사라지는 유일한 경로는 내보내기로 `lastBackupAt`이 갱신되는 것이다(R10). 근거: 데이터가 이 브라우저 안에만 있으므로 경고를 끄는 것은 위험을 지우는 게 아니라 숨기는 것이고, 끄는 행동 자체가 백업보다 싸서는 안 된다. pwa R6의 **저장 공간 배너와는 다른 것**이다 — 배너는 `persist()`가 거부됐을 때 1회만 뜨고 ✕로 닫으면 다시 뜨지 않는(기기별 기억) 일회성 알림이고, 경고 점은 조건이 참인 동안 계속 있는 상태 표시다.

  **임계 기간은 그 기록을 얼마나 믿을 수 있는지에 따라 둘이다 (사용자 결정, 2026-09-16).**

  | 내보내기 경로                                                 | 기록   | 점이 다시 뜨기까지         |
  | ------------------------------------------------------------- | ------ | -------------------------- |
  | 파일 피커로 저장 완료를 **관측함**(Chrome·Edge 등)            | 확인   | 30일 초과                  |
  | 앵커 내려받기 — 저장 성공을 **알 수 없음**(Firefox·Safari 등) | 미확인 | **15일 초과**(보통의 절반) |

  즉 "사라지는 유일한 경로는 내보내기"는 그대로지만, **미확인 내보내기가 사 오는 조용한 기간은 절반이다.** 갈라진 이유는 브라우저가 저장 성공을 알려주지 않기 때문이다 — `anchor.click()`은 사용자가 저장 대화상자를 취소하거나 정책·확장·디스크가 막아도 예외를 주지 않아, 그 경로에서 참인 것은 "파일을 넘겼다"까지다. 그런데도 **"일단 끄되 짧게 재무장"** 을 고른 근거: 점을 영구히 켜 두면(=미확인 내보내기를 인정하지 않으면) 사용자가 표시 자체를 무시하게 되어 경고의 목적이 무너지고, 반대로 전체 기간을 주면 저장되지 않았을 수도 있는 파일을 30일 동안 믿게 된다. 확인 버튼("저장했어요")을 두는 대안은 **이 규칙이 금지한 "끄는 조작"과 같아지므로** 택하지 않았다.

  화면 문구도 둘을 구분한다 — 확인된 기록은 `마지막 백업: 2026-09-01 (14일 전)`, 미확인 기록은 `백업을 시도했어요(저장 확인 안 됨): 2026-09-01 (14일 전)`. "백업함"과 "백업을 시도했어요"는 다른 사실이고, 확인하지 못한 것으로 안심시키지 않는다. 미확인 경로로 내보낸 직후에는 그 사실과 다시 알릴 시점을 문구로 알린다.

  기록이 없을 때(처음·사생활 보호 모드·저장소 차단·가져오기로 남의 `lastBackupAt`이 들어온 경우)는 전부 **미확인**으로 본다 — 읽기·쓰기 실패가 안전한 쪽으로 기운다.

## 4. 데이터

- domain: 백업 문서 타입, `validateBackup(json) → ok | { path, code }`, `planMerge(local, incoming) → { add, update, keep }`(순수 함수), 버전 변환 체인. 엔티티 타입 변경 없음(`Settings.lastBackupAt?` 추가).
- 레포지토리: **읽기** `DatasetRepository.readAll()` — 내보내기(R2)와 **병합의 현재 스냅샷(R6)** 둘 다 이 하나를 쓴다(툼스톤을 읽는 경로는 이것뿐이고, R2의 카테고리 tombstone도 여기서 나온다). **쓰기** `DatasetRepository.restore(snapshot)` 하나 — 병합·교체 모두 도메인이 `readAll()` 결과와 파일을 합쳐 **툼스톤을 포함한 최종 전량**을 계산해 이 한 메서드로 적용하므로 원자성이 모드와 무관하고(R7) 물리 삭제로 사라지는 정보가 없다(ADR-0009 결정 4). 인자는 plain 엔티티가 아니라 `PersistableSnapshot`이고, 파일에서 온 행은 도메인 `adopt(e)`가 시각·`rev`를 찍지 않고 브랜드만 붙여 만든다(그래야 R6 비교 기준과 R2 왕복이 산다 — TECH_PLAN §6, ADR-0009). 엔티티 레포지토리의 `upsert`는 가져오기에 쓰지 않는다.

## 5. 접근성

- 파일 선택은 실제 `input[type=file]`(시각적 커스텀 가능) + 선택된 파일명 텍스트. 모드는 `radiogroup`.
- 진행 중 `aria-busy="true"`, 완료 토스트 `role=status`, 오류 `role=alert`.
- 교체 모드의 확인 체크박스가 꺼져 있으면 `[가져오기]`는 `aria-disabled` + 이유 툴팁("확인 체크가 필요해요").

## 6. 범위 밖

- 자동 주기 백업, 클라우드 저장(Phase 2 sync), CSV/엑셀, 부분(날짜 범위) 내보내기, 다른 앱 형식 가져오기, 암호화.

## 7. 완료 조건

- [ ] R2~R9, R13 단위·계약 테스트(병합 케이스: 파일이 최신 / 로컬이 최신 / 로컬 삭제됨 / 파일에만 있음 / 동일 시각).
- [ ] **병합 데이터 손실 0**: 로컬 툼스톤 + 파일의 더 오래된 비삭제 같은 `id` → 병합 후에도 툼스톤이 남고(부활 0) 그 툼스톤이 저장된 전량에 있다. 그 카테고리를 가리키던 완료 투두가 category R17 "삭제됨" 그룹에 그대로 뜬다(계약 테스트, TECH_PLAN §6 ④).
- [ ] 내보낸 파일을 빈 브라우저 프로필에서 교체 가져오기 → 원본과 동일(세션 + **카테고리** tombstone 포함. 투두 tombstone은 R2가 내보내지 않으므로 왕복 대상이 아니다. E2E 또는 계약 테스트로 검증).
- [ ] 잘못된 파일 3종(비JSON, 타 앱, 필드 오류)의 문구가 R8과 일치.
- [ ] 키보드만으로 내보내기·가져오기 완료.
- [ ] 경고 점에 닫기 버튼·끄기 설정이 없다(R14). 조건이 거짓이 되면(내보내기 후) 사라진다.
- [ ] 미확인 내보내기는 점을 끄되 **절반 기간(15일) 초과**에 다시 뜬다. 확인된 내보내기는 30일 기준 그대로이고, 두 경로의 화면 문구가 다르다(R10·R14).
