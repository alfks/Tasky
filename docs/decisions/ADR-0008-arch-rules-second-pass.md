# ADR-0008: 아키텍처 규칙은 `--no-inline-config` 2차 패스로 강제한다

- 상태: accepted
- 날짜: 2026-09-15
- 관련: ADR-0006(결정 4 를 대체), docs/ARCHITECTURE.md §1, docs/conventions/code-style.md §7, eslint.arch.config.mjs, scripts/arch-layers.mjs, scripts/check-arch.sh

## 맥락

ESLint 는 "쓰인" `eslint-disable` 을 조용히 통과시킨다. 그래서 아키텍처 규칙(경계·표기·거울)을 지시자로 끄는 것을 막으려고 셸 검사기(`scripts/check-eslint-disable.sh`)를 두었는데, **세 라운드 연속 뚫렸다**. 매 라운드 새 문법 변형이 나왔다 — 따옴표 벗기기, 유니코드 공백(NBSP)을 구분자로 쓴 인라인 설정 주석, 정규식 리터럴·JSX 안 백틱으로 토크나이저 오염, 그리고 마지막에는 **빈 규칙 목록**: `/* eslint-disable , -- 사유 */` 한 줄이면 쉼표만 남은 목록을 ESLint 가 "빈 목록 = 파일 전체 비활성" 으로 읽어 그 파일의 모든 규칙이 꺼지는데, 검사기에게는 "규칙명이 있는" 문자열이라 세 게이트를 전부 통과했다(`,` `,,` `,,,,` `""` `,''` 및 `-line`·BOM·CR 개행 조합 9종).

원인은 개별 버그가 아니라 구조다: **ESLint 의 지시자 문법을 셸·정규식으로 재현하려 한 것**. 재현이 있는 한 다음 변형이 또 나온다. 덤으로 과잉 검출이 개발을 막았다(루트 헌법이 요구하는 `src/**/AGENTS.md` 에 disable 정책을 한국어로 적으면 실패, 주석에서 그 스크립트 파일명을 언급하면 실패, 템플릿 리터럴 줄이 `eslint `/`globals ` 로 시작하면 실패 — 실측 3종).

## 결정

**문법 파싱을 ESLint 에 맡긴다. 아키텍처 규칙만 담은 별도 flat config 로 `--no-inline-config` 2차 패스를 한 번 더 돌린다.**

1. `scripts/arch-layers.mjs` 가 아키텍처 규칙 목록의 단일 소스다 — `ARCH_RULES_COMMON`(공통 블록에서 켜는 규칙, **설정값까지** 여기 있다) + `ARCH_RULES_LAYER`(레이어 블록이 레이어마다 생성하는 경계 규칙) = `ARCH_RULES`.
2. `eslint.config.mjs`(1차 패스)는 그대로 둔다. 스타일 규칙의 정당한 disable(`// eslint-disable-next-line react/jsx-key -- 사유`)은 계속 허용되어야 한다 — 전체 설정에 `--no-inline-config` 를 걸면 그것까지 무력화되어 개발이 막힌다. 공통 블록은 `...ARCH_RULES_COMMON` 을 펼치기만 한다.
3. `eslint.arch.config.mjs`(2차 패스)는 **규칙을 다시 적지 않는다.** 1차 설정을 import 해 `ARCH_RULES` 에 없는 규칙만 지운다(`files`·`ignores`·plugins·parser·settings 는 그대로). 그래서 규칙 내용·옵션·레이어별 생성 결과가 1차와 어긋날 수 없다. `reportUnusedDisableDirectives` 는 이 패스에서만 끈다 — 방어적 설정이다(실측: ESLint 9 는 `--no-inline-config` 에서 미사용 지시자를 아예 보고하지 않는다. 그 동작에 기대지 않는다).
4. `scripts/check-arch.sh` 가 `eslint --no-inline-config -c eslint.arch.config.mjs src` 를 실제 `src/` 에 돌린다(그 명령은 스크립트 안 `arch_pass()` 한 곳에만 적혀 있다). 같은 실행의 JSON 결과로 **커버리지**도 본다: 트래킹된 `src` 코드 파일(`.ts`·`.tsx`) 중 하나라도 결과에 없으면 FAIL — 대상 경로를 좁히거나 전역 `ignores` 에 `src/…` 를 넣어 2차 패스를 조용히 비우는 변조가 여기서 잡힌다(실측). `node_modules` 가 필요하므로 CI 의 `guard` 가 아니라 `build` 잡(`check.sh --build`)에 있고, 스캐폴딩 전에는 `check-arch.sh` 가 통째로 SKIP 한다.
5. 같은 스크립트가 2차 패스가 **살아 있는지** 픽스처 5건으로 확인한다: 빈 규칙 목록·규칙명 없는 disable·제한 규칙 명시 disable·NBSP 인라인 설정 주석·삼중슬래시 + 그 규칙 disable. 판정 기준은 "1차에서는 0건(지시자가 실제로 먹힘 = 음성 대조) **그리고** 2차에서는 1건 이상". 픽스처는 명령을 따로 조립하지 않고 결정 4 의 `arch_pass()` 를 그대로 호출한다 — 따로 조립하면 실제 실행 줄에서 `--no-inline-config` 를 지워도 픽스처가 전부 PASS 한다(실측으로 그 상태였다).
6. 목록이 갈라지면 **설정 로드 시점에 throw** 한다 — 가드 4(경계 헬퍼가 만드는 규칙 ⊆ `ARCH_RULES`, 1차 설정에서), 가드 5(`ARCH_RULES_COMMON` 이 공통 블록에서 그 값 그대로 켜져 있는지 + 레이어 규칙이 어딘가에서 `'off'` 가 아닌지, 2차 설정에서), 가드 6(파생 결과에 규칙이 하나도 없으면 2차 패스가 조용히 무검사가 된다). 목록을 줄이려면 두 파일을 고쳐야 한다.
7. `scripts/check-eslint-disable.sh` 는 삭제한다. 스타일 규칙 disable 에 사유를 적는 것은 **리뷰 항목**으로 남긴다(도구로 강제하지 않는다 — 그 강제가 바로 위 과잉 검출의 출처였다).
8. **남는 한계**(실측으로 뒷받침되는 것만 적는다): ① 2차 패스의 범위는 `src/` 다. 레포 루트나 `src/` 밖에 둔 코드 파일은 아키텍처 규칙을 받지 않는다(위치 규칙은 DIRECTORY_MAP.md + 리뷰). ② 설정을 고치는 diff 는 대부분 도구가 잡지만 전부는 아니다. 실측: 규칙 목록이 갈라지는 방향은 가드 4~6 이 로드 시점에 죽이고, **한 파일 한 줄**짜리 변조도 `check-arch.sh` 가 잡는다(전역 `ignores` 에 `src/…` 추가·2차 패스 대상 축소 → 커버리지 검사, `--no-inline-config` 제거·`ARCH` 필터 축소 → disable 픽스처, 허용 목록 확대·레이어 규칙 `off` → 경계 픽스처). 도구가 보지 못하는 것은 **검사를 부르는 쪽을 지우는 diff** 다 — `scripts/check.sh` 의 `step_arch` 한 줄, `.github/workflows/ci.yml` 의 build 잡, `check-arch.sh` 자체의 삭제, 그리고 `tsconfig.json` 의 `@/*` 별칭. 이런 계열은 사람이 본다(위 넷은 실측으로 확인한 예시이지 닫힌 목록이 아니다). ③ ESLint 가 파싱하지 못하는 파일은 fatal 로 보고되므로 조용히 빠지지는 않는다. ④ `.md` 는 레이어 분류 대상이 아니므로, 문서만 담은 미등록 디렉토리는 전수 분류를 통과한다(코드 파일을 넣는 순간 실패한다). 같은 레이어에서 `@/…/AGENTS.md` 를 import 하는 것도 린트는 통과하지만 `tsc` 가 TS2307 로 거부한다.

## 대안과 기각 이유

| 대안                                             | 기각 이유                                                                                                                                                |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 셸 검사기를 다시 고친다(빈 목록 파싱 추가)       | 네 번째 수정이다. 매 라운드 "이번엔 ESLint 와 맞췄다" 가 뒤집혔다 — 재현이 있는 한 다음 변형이 또 나온다. 과잉 검출로 개발을 막는 부작용도 그대로 남는다 |
| 전체 설정에 `linterOptions.noInlineConfig: true` | 스타일 규칙의 정당한 disable 까지 무력화된다. 그러면 `react/jsx-key` 같은 규칙을 아예 끄거나 코드를 왜곡해야 한다 — 스캐폴딩 티켓이 바로 막힌다          |
| 2차 설정에 규칙을 **다시 적는다**                | 지금까지 구멍이 난 자리가 대부분 "목록이 두 군데로 갈라짐" 이었다(거울 누락, zone↔문자열 패턴 불일치). 1차에서 파생하면 갈라질 수 없다                   |
| `eslint-plugin-eslint-comments` 의 `no-use` 등   | 지시자를 규칙으로 검사하는 것이라 **그 규칙 자체를 지시자로 끌 수 있다**(순환). devDependency +1 로 얻는 보장이 0                                        |

## 결과

- 좋은 점: 라운드 3 이 찾은 우회 전부(빈 목록 Blocker 포함)와 새로 고안한 우회가 **문법과 무관하게** 차단된다 — 파싱을 ESLint 가 하므로 재현 오류가 생길 자리가 없다. 셸 스크립트 하나(113줄)가 사라지고 과잉 검출 3종도 함께 사라졌다. 추가 의존성 0.
- 감수하는 점: `pnpm lint` 와 별도로 ESLint 가 한 번 더 돈다(파일 200개에서 약 5초, 1차와 비슷). 스타일 규칙 disable 의 "사유 필수" 가 도구 강제에서 리뷰 항목으로 내려간다.

## 지켜야 할 규칙 (검증 가능한 문장 — 리뷰 판정 근거)

1. 아키텍처 규칙을 추가·삭제하려면 `arch-layers.mjs` 의 `ARCH_RULES_*` 와 `eslint.config.mjs` 를 같은 PR 에서 고친다. 한쪽만 고치면 `pnpm lint` 또는 2차 패스가 로드 시점에 죽는다(가드 4~6, 음성 대조 실측).
2. `eslint.arch.config.mjs` 에 규칙 이름을 직접 적지 않는다 — 1차 설정에서 파생한다.
3. `bash scripts/check-arch.sh` 가 매 CI 에서 2차 패스(+ 커버리지) + 픽스처 5건 PASS. 새 우회 문법을 발견하면 픽스처를 늘린다. 2차 패스의 명령을 픽스처가 따로 조립하지 않는다 — 실행하는 줄과 검증하는 줄이 갈라지면 검증이 거짓이 된다(실측으로 그랬다).
4. ESLint 의 문법을 셸·정규식으로 재현하는 검사기를 다시 만들지 않는다(scripts/AGENTS.md 규칙 8).

## 재검토 트리거

- 2차 패스가 1차 패스보다 오래 걸리거나 `src/` 파일이 600개를 넘으면(현재 0 — 스캐폴딩 전) 캐시(`--cache`) 도입을 검토한다.
- `ARCH_RULES` 가 15개를 넘으면(현재 9) "아키텍처 규칙" 의 정의가 넓어진 것이므로 목록을 다시 본다.
- `src/` 밖에 코드 파일을 두어야 할 일이 생기면(예: 루트 `instrumentation.ts`) 결정 8 ①의 한계를 닫는 ADR 을 쓴다.
