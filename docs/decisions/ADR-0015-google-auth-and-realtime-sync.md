# ADR-0015: 구글 로그인을 필수로 두고 Cloudflare D1 로 준실시간 동기화한다

- 상태: accepted
- 날짜: 2026-09-18
- 관련: ADR-0013(배포 스택 — **개정**: "Worker 스크립트 없음" 이 더는 참이 아니다) · ADR-0007(저장소 계약) · ADR-0009(데이터셋 연산) · `docs/specs/product-overview.md` Phase 2 · 티켓 T-72~T-77

## 맥락

지금까지 이 앱은 **로컬 우선**이었다. 계정이 없고 서버가 없고, 데이터는 브라우저 IndexedDB 에만 있다.
`wrangler.jsonc` 주석이 그 전제를 그대로 적고 있다 — _"Worker 스크립트가 없다: SPA 라 서버에서 할 일이 0"_.
README 도 _"계정도, 서버도, 추적도 없습니다"_ 라고 약속한다. 기기 간 이동 수단은 백업 파일 내보내기/불러오기뿐이다.

사용자가 요구한 것(2026-09-18, 원문):

> 로그인을 할 수 았는 페이지가 먼저떠서 핸드폰으로 들어가든 웹으로 들어가든 아이디로 연동될 수 있게했으면 좋겠어
> 또한 웹에서 할일추가, 카테고리 생성, 할일의 카테고리 변경과 같은 변경사항이 들어왔을 때 동시에 함께 옮겨졌으면 좋겠어

그리고 네 갈래를 사용자가 직접 골랐다: **구글 소셜 로그인** · **Cloudflare D1 + Workers** ·
**로그인 필수(로그인 페이지가 먼저)** · 실시간성은 처음에 "진짜 실시간" 을 골랐다가
**준실시간으로 내렸다**(2026-09-18, 아래 §변경 이력).

**이것은 기능 추가가 아니라 제품 성격의 변경이다.** 로컬 전용에서 계정 기반 서버 동기화로 넘어간다.
그래서 ADR 로 남긴다.

## 결정

### 1. 신원 — 구글 OAuth 2.0 Authorization Code + PKCE, 세션은 서버가 쥔다

- 교환(코드 → 토큰)은 **Worker 에서만** 한다. 클라이언트 시크릿이 브라우저에 내려가지 않는다.
- 브라우저에는 **구글 토큰을 저장하지 않는다.** Worker 가 자체 세션을 발급해
  `HttpOnly` · `Secure` · `SameSite=Lax` 쿠키로 준다. XSS 로 세션을 읽어갈 수 없다.
- 사용자 식별자는 구글 `sub` 다(이메일이 아니다 — 이메일은 바뀔 수 있고 재사용될 수 있다).

### 2. 권위 — 서버가 진실이고 IndexedDB 는 캐시다

로그인을 **필수**로 둔 순간 "로컬이 원본" 은 성립하지 않는다. 두 기기가 같은 계정을 보는데
양쪽 다 원본이면 병합 규칙이 제품 규칙이 되어 버린다. 그래서:

- **서버(D1)가 단일 진실**이다. 모든 레코드는 서버가 발급한 단조 증가 `rev` 를 갖는다.
- **IndexedDB 는 캐시 + 오프라인 큐**다. 지금의 `repositories` 인터페이스(ADR-0007)는 그대로 두고,
  **동기화하는 구현체를 하나 더** 만든다. 화면 코드는 바뀌지 않는다 — 그게 저장소를 인터페이스 뒤에
  둔 이유였고, 여기서 값을 회수한다.
- 충돌은 **레코드 단위 last-write-wins**(서버 `rev` 기준). 필드 단위 병합은 하지 않는다 —
  할 일 앱에서 같은 레코드를 두 기기가 동시에 고치는 일은 드물고, 필드 병합은 복잡도에 비해 값이 작다.

### 3. 준실시간 — `rev` 델타 풀 하나로 맞춘다 (상시 연결 없음)

- **쓴 기기는 즉시 반영된다**(낙관적 갱신 + HTTP 커밋). 느린 쪽은 **다른 기기가 따라오는 시간**이다.
- 다른 기기는 아래 순간에 **마지막으로 본 `rev` 이후만** 당겨온다(전량 재조회 없음):
  1. 앱이 앞으로 나올 때(`visibilitychange` · `focus`)
  2. 온라인으로 복귀할 때(`online`)
  3. 보이는 동안 주기적으로(간격은 구현 티켓에서 정하고 근거를 적는다)
- **상시 연결(WebSocket·Durable Objects)을 두지 않는다.** 원래 설계에서도 연결은 편의였고
  **정확성의 근거는 `rev` 델타 풀** 이었다 — 그래서 푸시 계층만 빼면 정확성 모델은 그대로다.
  나중에 진짜 실시간이 필요해지면 **이 위에 푸시를 얹기만** 하면 된다(§재검토 트리거).

### 4. 오프라인 — 첫 로그인만 온라인, 그 뒤로는 계속 쓸 수 있다

로그인 필수는 **첫 실행에 네트워크를 요구한다.** 그 대가를 줄이기 위해:

- 세션이 살아 있으면 **오프라인에서도 읽고 쓸 수 있다.** 쓰기는 로컬에 쌓이고 온라인 복귀 때 올라간다.
- 오프라인 상태를 **화면에 정직하게 표시한다.** "저장됨" 처럼 보이는데 서버에 없는 상태를 숨기지 않는다.

### 5. 기존 로컬 데이터 — 지우지 않는다. 첫 로그인 때 사용자가 정한다

이미 쓰던 사람의 IndexedDB 에 데이터가 있다. 로그인 필수로 바뀌었다고 **말없이 버리지 않는다.**
첫 로그인 시 "이 기기에 있던 N건을 계정으로 올릴까요?" 를 묻고, 올리기/그대로 두기를 고른다.
백업/복원(ADR-0009)이 이미 같은 모양의 문제를 풀어 뒀으니 그 경로를 재사용한다.

## 결과 (좋은 것과 나쁜 것 모두)

**얻는 것**: 기기 간 연동 · 브라우저 데이터를 지워도 살아남음 · 계정 하나로 폰/웹.

**잃는 것 — 숨기지 않고 적는다**

1. **"계정도, 서버도, 추적도 없습니다" 가 거짓이 된다.** README 의 그 약속은 **반드시 고쳐야 한다**(T-77).
   고치지 않고 배포하면 사실이 아닌 프라이버시 주장을 하는 것이다.
2. **가입 전에는 앱을 볼 수 없다.** 로그인 필수를 고른 대가다. 첫 방문자의 이탈이 늘어난다.
3. **비용** — 준실시간으로 내린 덕에 **Cloudflare 무료 한도 안에서 시작할 수 있다**(D1 만 쓰고
   Durable Objects 를 쓰지 않는다). 진짜 실시간을 골랐다면 Workers Paid(월 $5~)가 사실상 필요했다.
4. **자격증명이 늘어난다**: 구글 OAuth 클라이언트 ID/시크릿, D1 데이터베이스 ID.
   지금의 `CLOUDFLARE_*` 두 개에 더해 사용자가 직접 발급해야 한다.
5. **서버가 생기면 지켜야 할 것이 생긴다**: 세션 만료·로그아웃·계정 삭제·데이터 내보내기.
   법적 의무(개인정보 처리방침)는 이 ADR 의 범위 밖이지만 **배포 전에 필요하다**.

## 대안과 기각 이유

| 대안                                        | 기각 이유                                                                                                                                                                                     |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 로그인 선택(로컬 전용 모드 유지)            | 사용자가 **필수**를 명시적으로 골랐다. 기술적으로는 이쪽이 안전하지만 그건 제품 결정이고 사용자 몫이다. 다만 §4·§5 로 대가를 줄인다                                                           |
| 진짜 실시간(Durable Objects + WebSocket)    | **채택했다가 내렸다**(§변경 이력). 상시 연결은 Workers Paid 가 사실상 필요하고 재연결·유실 처리가 붙는다. 정확성은 어차피 `rev` 델타 풀이 만들므로, 먼저 값싼 쪽으로 세우고 필요해지면 얹는다 |
| Supabase · Firebase                         | 인증·DB·실시간이 이미 조립돼 있어 만들 것이 적다. 그러나 배포 대상이 이미 Cloudflare 라 업체가 하나 늘고, Firebase 는 데이터가 구글에 종속돼 이전이 어렵다. 사용자가 Cloudflare 를 골랐다     |
| 이메일+비밀번호                             | 재설정 메일·해싱·유출 대응을 직접 만들어야 하고 메일 발송 업체가 또 필요하다. 구글 로그인이 만들 것이 가장 적다                                                                               |
| 클라이언트가 구글 토큰을 직접 들고 API 호출 | 토큰이 브라우저에 남아 XSS 한 번에 계정이 털린다. 서버 세션 쿠키가 표준적이고 안전하다                                                                                                        |
| CRDT(필드 단위 자동 병합)                   | 할 일 앱의 충돌 빈도에 비해 복잡도·번들 크기가 과하다. 진입 청크 예산이 gzip 150,000 B 인데 지금 130,752 B 로 여유가 19 kB 뿐이다                                                             |
| WebSocket 만으로 상태를 맞춤(풀 없이)       | 끊김·재연결·메시지 유실에서 조용히 틀려진다. **연결은 편의, 정답은 `rev` 델타 풀** 이어야 한다                                                                                                |

## 변경 이력

- **2026-09-18 (최초)**: 네 갈래를 사용자가 고름 — 구글 · D1 · 로그인 필수 · **진짜 실시간**(Durable Objects).
- **2026-09-18 (개정, 이 문서의 현재 내용)**: 사용자가 _"그럼 일단 준실시간으로 가자"_ 로 실시간성만 내렸다.
  **구현이 시작되기 전이라 결정 §3 을 그대로 고쳤다**(별도 ADR 로 supersede 하지 않는다 — 한 번도
  살아 본 적 없는 결정을 문서 두 개로 남기면 읽는 사람이 어느 쪽이 진짜인지 매번 확인해야 한다).
  나머지 셋(구글 · D1 · 로그인 필수)은 **바뀌지 않았다.**
- **2026-09-20 (정정)**: 위 개정에서 §3 결정("상시 연결을 두지 않는다 — DO 없음")을 고쳤는데
  "결과" 절 4번의 자격증명 목록에는 "DO 바인딩" 이 그대로 남아 있었다. 실제로 DO 를 쓰지 않으므로
  발급할 DO 바인딩도 없다 — 목록에서 뺐다. 결정 자체(§3)는 바뀌지 않는다.

## 재검토 트리거

- 다른 기기가 따라오는 지연이 실제로 거슬리면 → **이 설계 위에 푸시 계층을 얹는다**(Durable Objects).
  델타 풀은 그대로 두고 "언제 당길지" 의 신호가 하나 늘 뿐이라 되돌릴 것이 없다.
- 동시 편집 충돌이 실제로 문제가 되면 → 레코드 LWW 대신 필드 병합을 재검토한다.
- 첫 방문 이탈이 문제가 되면 → 로그인 선택(둘러보기 모드)을 재검토한다.
