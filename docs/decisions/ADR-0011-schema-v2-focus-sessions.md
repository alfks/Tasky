# ADR-0011: 스키마 v2 — `focusSessions` 테이블 신설과 `categories` 인덱스 확장

- 상태: accepted
- 날짜: 2026-09-16
- 관련: 티켓 T-10, ADR-0002(규칙 3 마이그레이션), ADR-0005, ADR-0009, docs/TECH_PLAN.md §5, docs/ARCHITECTURE.md §4

## 맥락

`db.ts` 의 v1 은 `todos`·`categories`·`settings` 3 테이블이고 `categories` 인덱스는 `id, order` 다. 그런데 도메인에는 `FocusSession` 이 있고(`FocusSessionRepository` 계약과 계약 테스트가 이미 존재), TECH_PLAN §5·ARCHITECTURE §4 는 `focusSessions: id, todoId, date, status, updatedAt` 와 `categories: id, order, status, updatedAt` 를 이미 선언하고 있다. 즉 **코드가 문서보다 한 버전 뒤**다. IndexedDB 스키마 버전업은 ADR 필수(`docs/decisions/AGENTS.md`)이고, 인덱스 추가·테이블 신설은 비인덱스 필드 추가와 달리 버전업 대상이다(TECH_PLAN §5 규칙 3).

## 결정

**`db.version(2)` 를 추가해 `focusSessions` 테이블을 신설하고 `categories` 에 `status`·`updatedAt` 인덱스를 더한다. `version(1)` 블록은 `STORES_V1` 로 보존하고 수정하지 않는다.**

1. **v1 사용자가 없어도 version(2) 로 올린다.** 배포 전이라 `stores` 를 v1 에 덧쓰는 편이 짧지만, 그러면 첫 마이그레이션이 필요해지는 날 본보기가 없다. 여기서 경로를 한 번 밟아 두고 `migration.test.ts` 가 그 경로를 고정한다.
2. **`.upgrade()` 콜백을 달지 않는다.** 두 변경 모두 기존 로우의 **값을 바꾸지 않는다** — 테이블 신설은 빈 스토어를 만들 뿐이고, 인덱스 추가는 IndexedDB 가 기존 로우를 재색인한다. 이 주장은 주석이 아니라 테스트로 뒷받침한다: v1 로 넣은 카테고리가 v2 의 `status`·`updatedAt` 인덱스로 조회되는지를 단언한다. 값 변환이 필요한 다음 버전업은 규칙대로 `.upgrade()` 를 단다.
3. **`DB_VERSION` 상수를 `db.ts` 에서 내보낸다.** 백업 파일의 `schemaVersion` 은 이 상수 하나에서 파생한다(TECH_PLAN §5 규칙 6) — 숫자를 두 곳에 적지 않는다.
4. **`categories` 인덱스 확장을 같은 버전에 묶는다.** 지금 쓰는 조회는 없지만(카테고리 목록은 `order` 인덱스), 문서가 이미 선언한 스키마와 코드를 갈라 둔 채로 두면 다음 사람이 "문서가 맞나 코드가 맞나" 를 다시 조사한다. 버전업 비용은 한 번뿐이므로 한 번에 맞춘다.

## 대안과 기각 이유

| 대안                                         | 기각 이유                                                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `version(1)` 의 `stores` 를 고쳐서 4테이블로 | 배포 전이라 당장은 동작하지만 "기존 버전 블록 수정 금지"(TECH_PLAN §5 규칙 1)를 첫 사례부터 어긴다                  |
| `focusSessions` 를 T-23(타이머) 때 추가      | `FocusSessionRepository` 계약 테스트가 지금 이 테이블을 요구한다 — 계약은 있는데 저장할 곳이 없는 상태가 남는다     |
| `categories` 인덱스는 실제 조회가 생길 때    | 버전업이 두 번이 되고, 그때까지 ARCHITECTURE §4 의 선언이 코드와 어긋난 채 남는다                                   |
| 빈 `.upgrade(() => {})` 를 형식상 추가       | 하는 일이 없는 코드가 "여기서 뭔가 변환한다" 는 잘못된 신호를 준다. 필요 없다는 근거는 마이그레이션 테스트가 남긴다 |

## 결과

- 좋은 점: 도메인 5 타입이 모두 저장 위치를 갖는다. 마이그레이션 경로(v1 픽스처 → v2 열기 → 단언)가 테스트로 실재해 다음 버전업이 복사할 본보기가 된다. 문서(TECH_PLAN §5·ARCHITECTURE §4)와 코드의 스키마 문자열이 일치한다.
- 감수하는 점: `STORES_V1` 이라는, 앱 코드가 쓰지 않고 마이그레이션 테스트만 쓰는 상수가 남는다(버전이 늘수록 이런 상수가 쌓인다 — 세 개를 넘어가면 `stores-history.ts` 로 분리한다). `categories` 의 새 인덱스 둘은 당분간 조회처가 없어 쓰기 비용만 든다(로우당 인덱스 2개, 카테고리는 수십 건 규모라 예산 밖이 아니다).
- 측정한 것/측정하지 않은 것: 업그레이드 후 재색인은 fake-indexeddb 에서 확인했다. **실제 브라우저 엔진에서는 확인하지 않았다** — IndexedDB 재색인은 명세 동작이라 같을 것으로 보지만, E2E(T-24) 가 실기기에서 한 번 확인하기 전까지는 근거가 fake-indexeddb 한 곳이다.

## 지켜야 할 규칙 (검증 가능한 문장 — 리뷰 판정 근거)

1. `STORES_V1` 과 `db.version(1)` 블록은 수정하지 않는다. 스키마 변경은 `version(n+1).stores(...)` 추가로만 한다.
2. 스키마 버전을 올리는 PR 은 ADR + `db.ts` + 마이그레이션 테스트(v_n 픽스처 → v_{n+1} 열기 → 단언)를 함께 담는다(TECH_PLAN §5 규칙 5).
3. `.upgrade()` 를 생략하는 버전업은 "기존 로우의 값을 바꾸지 않는다" 를 **테스트로** 보여야 한다. 보이지 못하면 `.upgrade()` 를 단다.
4. 마이그레이션 테스트는 각 케이스 전에 DB 를 지운다. 지우지 않으면 첫 케이스가 올려놓은 v_{n+1} DB 위에서 돌아 업그레이드를 한 번도 밟지 않는다(실측).
5. 스키마 버전 숫자는 `DB_VERSION` 한 곳에만 적는다.

## 재검토 트리거

- 값 변환이 필요한 버전업(필드 타입 변경·필수 필드 추가)이 처음 생길 때 — `.upgrade()` 실패를 `RepositoryError('SCHEMA_UPGRADE_FAILED')` 로 옮기는 경로(TECH_PLAN §5 규칙 4)가 아직 배선되지 않았으므로 그 티켓에서 함께 만든다.
- 보존해야 할 `STORES_V*` 상수가 3개를 넘을 때.
