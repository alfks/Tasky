# ADR-0020: 다기기 세션 — 세션 전량 폐기는 재가입 경로에서만, 취소는 명시적 `logout-others` 로

- 상태: accepted
- 날짜: 2026-09-21
- 관련: 사용자 보고(같은 계정으로 웹앱·웹사이트를 동시에 열면 한쪽이 로그아웃됨), ADR-0015(§1 로그인 필수·세션
  발급) · ADR-0019(§결정 3·4 계정 삭제·세션 검증 — **결정 5 의 근거를 이 문서가 부분 대체**), `worker/auth/AGENTS.md`,
  docs/specs/sync.md §4·§6, SYNC_DESIGN.md §②-3

## 맥락

`handleCallback`(`worker/auth/handlers.ts`)과 `handleStubLogin`(`worker/auth/stub.ts`)은 로그인마다 무조건
`DELETE FROM sessions WHERE sub = ?` 를 돌렸다. 이 문장은 "삭제 창 동안 요청을 한 번도 안 보낸 탈취 세션이
재가입으로 되살아나는" 실제 취약점을 막으려던 것(#126 리뷰, D1 재현)이지 다기기를 막으려던 것이 아니다.
SYNC_DESIGN.md §②-3 은 `/auth/logout` 을 "자기 `sid` 행만 삭제(다른 기기 유지)" 로 이미 적어 두었다 —
기기마다 세션이 따로 사는 것이 원래 설계였고, 로그인 시점의 전량 폐기가 그 설계와 어긋나 있었다.

## 결정

1. **세션은 로그인(기기)마다 하나이고, 같은 `sub` 에 N 개가 동시에 유효할 수 있다.**
2. **세션 전량 폐기(`DELETE FROM sessions WHERE sub = ?`)는 `deleted_users` 에 그 `sub` 행이 있을 때만**
   실행한다 — 판정과 폐기를 `… WHERE sub = ? AND EXISTS (SELECT 1 FROM deleted_users WHERE sub = ?)` 한 문장으로
   쓰고, `deleted_users` 삭제·`users` upsert 와 함께 `db.batch()` 한 트랜잭션에 넣어 순서(폐기 → 표식 삭제 →
   upsert → 세션 발급)를 고정한다. 평범한 재로그인은 다른 기기의 세션을 건드리지 않는다.
3. 두 로그인 경로(구글 콜백·로컬 스텁)는 이 순서를 `worker/auth/session.ts#signIn` 함수 하나로 합쳐서 부른다 —
   "두 파일이 같은 순서를 지킨다"는 사람 규칙을 구조로 바꾼다.
4. **스키마 변경 없음, 마이그레이션 없음, 클라이언트 프로토콜 변경 없음.** `sessions.device_id` 는 이번에
   넣지 않는다 — 기기 목록·기기별 취소는 스펙에 없는 별도 제품 기능이다.
5. **취소 수단을 명시적으로 되돌린다**: 같은 작업 안에서 `POST /auth/logout-others`("다른 기기 모두
   로그아웃")를 후속 PR 로 추가한다(제품 소유자 승인). `worker/auth/session.ts` 에 `destroyOtherSessions(sub, sid)`
   를 두고, `SyncTransport` 포트(ADR-0018)에 `logoutOthers()` 메서드를 더한다 — 이 시그니처 변경을 이 ADR 이 기록한다.

## 대안과 기각 이유

| 대안                                                                       | 기각 이유                                                                                                                                                                                       |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessions.device_id` 추가 + 기기별 세션·기기 목록 UI                       | 공격을 막는 데 기여하지 않는다(재가입 폐기는 어차피 `sub` 단위여야 한다). 사는 것은 스펙에 없는 제품 기능("기기 목록")이다 — 나중에 붙일 때 이 결정을 되돌릴 것은 없다                          |
| 계정 삭제 시점에 다른 기기 세션도 즉시 지움(그러면 재가입 폐기가 불필요)   | ADR-0019 §결정 3 이 명시적으로 기각한 것과 같다 — 다른 기기가 `sub` 를 못 찾아 410(계정 삭제 안내) 대신 평범한 401 을 받는다. 그리고 그것만으로는 로그인 시 전량 폐기가 남아 증상이 안 고쳐진다 |
| 세대 번호(`session_epoch` 또는 `deleted_at` 과 `sessions.created_at` 비교) | 재가입 시점엔 "그 `sub` 의 기존 세션 = 전부 삭제 이전 세션" 이라 구분할 이유가 없다(보조정리). 결과는 조건부 폐기와 같으면서 컬럼·시계 비교가 하나 더 생긴다                                    |
| 현상 유지(무조건 폐기, 문서화만)                                           | ADR-0015 의 존재 이유("어느 기기로 들어가든 이어진다")를 부정한다. 사용자가 버그로 보고했다                                                                                                     |

## 결과

- 좋은 점: 두 기기 동시 로그인이 서로를 끊지 않는다. 재가입(삭제 뒤 같은 계정으로 재가입) 경로의 방어는
  그대로다 — 보조정리(재가입 시점 직전의 `sub` 세션은 전부 삭제 이전 것)로 증명된다. diff 가 작다(스키마·
  클라이언트 변경 없음).
- 감수하는 점: 무조건 폐기가 우연히 주던 "아무 기기에서나 재로그인하면 모든 세션이 죽는" 전량 취소 수단이
  없어진다. **탈취된 세션은 슬라이딩 갱신(만료 7일 미만이면 30일 연장) 덕에 공격자가 주 1회만 써도 무기한
  산다** — 결정 5 의 `logout-others` 가 이 공백을 메우는 목적이다.
- 감수하는 점: 재가입이 다른 정당한(삭제 창 동안 오프라인이었던) 기기의 세션도 함께 지운다 — ADR-0019
  §결정 5 괄호의 시나리오 그대로이며 이번 변경으로 달라지지 않는다.

## 지켜야 할 규칙 (검증 가능한 문장 — 리뷰 판정 근거)

1. `sessions` 를 `sub` 단위로 지우는 문장은 `session.ts#signIn`(재가입)과 `#destroyOtherSessions`
   (`logout-others`) 두 곳에만 있다 — 다른 곳에 새로 생기면 막는다.
2. 폐기 판정(`EXISTS (SELECT 1 FROM deleted_users …)`)과 실제 삭제는 **한 SQL 문**이다 — 나누면 batch 밖에서
   TOCTOU 가 생긴다.
3. `worker/account/delete.test.ts` 의 탈취 세션 시나리오(ADR-0019 확인 경로)는 지우지 않는다 — 이번 변경이
   막는 공격이 회귀하지 않았음을 그 테스트가 계속 증명한다.

## 관계

ADR-0019 §결정 5 의 근거 문단("다른 기기가 말없이 데이터를 되살리는 위험은 이 경로에서 나지 않는다")을
**부분 대체**한다 — 실제로는 그 경로(무조건 폐기)에서 위험이 났었다(§맥락). ADR-0019 §결정 1~4, §재검토
트리거는 그대로 유지된다. ADR-0019 파일 자체는 고치지 않는다 — 이 문서가 개정 기록을 대신 남긴다.

## 재검토 트리거

- 기기 목록·기기별 개별 취소가 제품 스펙(sync.md)에 들어오면 `sessions.device_id` 를 다시 검토한다.
- `logout-others` 없이 이 결정만 배포하기로 뒤집히면(제품 소유자 재결정), §결과 "감수하는 점"의 무기한
  생존 위험이 완화 없이 남는다는 사실을 다시 따진다.
