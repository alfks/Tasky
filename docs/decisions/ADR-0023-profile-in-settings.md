# ADR-0023: 개인 프로필은 `Settings` 행의 세 필드 — 사진은 클라이언트가 줄인 데이터 URL

- 상태: accepted
- 날짜: 2026-09-29
- 관련: [profile.md](../specs/profile.md) · 티켓 T-A(이 문서)·T-G(구현) · ADR-0005(공통 필드·충돌 정책)·ADR-0018(로우 단위 LWW·동기화 테이블)·ADR-0022(소셜 프로필은 별개)
- 구현: 예정(T-G). 이 결정의 승인은 기능 출시를 뜻하지 않는다.

## 맥락

사용자 피드백 3번 — "내 이름·사진·한 줄 소개를 앱에 두고 싶다". 이름·소개는 짧은 문자열이지만 사진은 **이진 데이터**라 지금까지 동기화·백업 경로에 실어 본 적이 없는 종류다. 개인 자료는 `entities(sub,tbl,id)` 로우 JSON 을 `updatedAt` LWW 로 맞추는 동기화(ADR-0018)·JSON 백업(backup.md)·D1 `body TEXT` 를 이미 갖고 있다. 로우 본문의 검증은 **한 함수**(`src/domain/backup/validate-rows.ts` 의 화이트리스트 `readSettings`)를 백업 복원·동기화 풀·**Worker 푸시**(`readRemoteRow`) 세 곳이 import 해 쓴다 — Worker 는 화이트리스트를 통과한 필드만 저장한다. 구글에는 `openid email` 만 요청하므로(README·privacy.html) 이름·사진은 구글이 주지 않고 사용자가 직접 적는다.

## 결정

프로필 세 값을 **`Settings` 단일 행의 선택 필드** `profileName`·`profileBio`·`profileAvatar` 로 둔다. 사진은 **클라이언트가 96×96 으로 줄여 인코딩한 데이터 URL 문자열**(`data:image/webp;base64,…` 또는 `image/jpeg`, **문자열 길이 ≤ 16,384자 ≈ 이진 12 KB** — 상한과 품질 하강 문턱은 이 하나뿐이다)이고 원본은 저장하지 않는다. 형식이 틀린 프로필 필드는 **행을 거부하지 않고 그 필드만 버린다**. `Settings` 는 로우 단위 LWW 라 다른 필드와의 동시 편집 경합을 감수한다.

- 동기화·백업이 공짜다 — Worker 가 안 보기 때문이 아니라 **Worker 가 `src/domain` 의 같은 `readSettings` 를 import 하기 때문**이다. `SETTINGS_KEYS` 에 세 필드를 더하면 백업 복원·풀·Worker 푸시 셋이 함께 받아들이고, `worker/**` 런타임 코드·D1 마이그레이션·`server-rules.vectors.ts`(LWW 규칙용 — 화이트리스트 검사는 벡터 대상이 아니다)·`DB_VERSION` 변경이 **0** 이다(Dexie `settings: 'id'` — 새 필드에 인덱스 없음). 대신 **확장된 번들로 Worker 를 재배포하기 전에는 프로필이 동기화되지 않는다**(아래 "감수하는 점").
- ≈12 KB 이진(16,384자) 하나는 동기화 배치(500건)·요청 본문 2 MB·백업 파일(≤20 MB)·D1 `body TEXT` 어디에도 부담이 아니다. 상한을 문자열 길이로 고정해 어느 기기·어느 경로에서도 같은 값으로 검사한다.
- 백업 복원·풀·푸시에서 사진 하나가 깨졌다고 설정 행 전체(테마·강조색·시드 표식)를 잃으면 안 된다 — 필드 단위 폐기가 사용자에게 덜 파괴적이다.
- 개인 프로필은 **나만 보는 값**이다. 소셜 별명(`social_profiles.nickname`, ADR-0022)과 저장소·공개 범위가 다르므로 섞지 않는다.

## 대안과 기각 이유

| 대안                                          | 기각 이유                                                                                                                                                                |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 새 테이블 `profile` (+ D1 마이그레이션)       | `tbl IN (…)` CHECK 변경(마이그레이션 0003)·동기화 테이블 목록·Dexie v5·백업 스키마·벡터 세 계층을 전부 건드린다 — 필드 셋을 위해 치를 값이 아니다.                       |
| 소셜 프로필(`social_profiles`) 확장           | social.md 는 "친구에게 보일 별명"만 공개하고 구글 이름·사진 자동 공개를 금지한다. 온라인 전용·서버 command 계약(ADR-0022 4)이라 오프라인 기기에서 내 이름조차 못 본다.   |
| 기기 로컬 전용(localStorage·`syncState`)      | 기기마다 다시 적어야 하고 백업에도 안 실린다. "동기화되는 앱"의 전제(sync.md R3)와 어긋나며, 사용자가 이름을 적었는데 다른 기기에서 비어 있는 상태를 설명할 방법이 없다. |
| 사진을 서버 객체 저장소(R2 등)에 올리고 URL만 | 새 런타임 의존·업로드 엔드포인트·인증·삭제 연쇄가 생긴다. 96px 아바타 하나에 과하고, 오프라인 첫 페인트에서 사진이 비게 된다.                                            |

## 결과

- 좋은 점: 서버 런타임·스키마·벡터 무변경. 오프라인에서도 프로필이 보인다. 백업 파일에 자동 포함되고 계정 삭제 시 설정 행과 함께 사라진다.
- 감수하는 점: (ㄱ) 기기 A 가 강조색, 기기 B 가 프로필을 **같은 순간** 고치면 한쪽이 진다 — 둘 다 눈에 보이는 값이라 다시 고치면 된다. 쓰기를 저장소에서 새로 읽은 행 위에 하면 같은 기기 안의 경합은 **사실상** 없다(두 스토어의 저장은 사용자 조작으로만 일어나고 읽고-고치고-쓰기는 트랜잭션이 아니다). (ㄴ) 설정 행이 최대 ~17 KB 커지고, 테마 토글·내보내기(`lastBackupAt`)처럼 설정 행을 건드리는 **모든 쓰기가 아바타를 다시 올린다**(로우 단위 동기화) — 무해하지만 설정 푸시 크기를 추적할 때 여기로 온다. (ㄷ) 사진 원본 해상도는 버린다. (ㄹ) **혼합 버전**: 서비스워커에 캐시된 옛 클라이언트(세 필드를 모르는 `SETTINGS_KEYS`)는 풀에서 세 필드를 떼어 저장하고 다음 설정 쓰기(테마 토글 등)로 떼인 행을 더 새 `updatedAt` 으로 올려 **모든 기기에서 프로필이 사라진다**("노트북에서 테마를 바꿨더니 프로필이 없어졌다"). 같은 부류로 **옛 Worker + 새 클라이언트**는 푸시를 `applied` 로 받으면서 세 필드를 조용히 떼어 "저장은 되는데 다른 기기에 안 뜬다". 완화: PWA 가 다음 로드에서 갱신되면 그치고, Worker 재배포는 T-G 출시 조건이며, 프로필은 다시 적으면 되고 백업 파일에는 남는다.

## 지켜야 할 규칙 (검증 가능한 문장 — 리뷰 판정 근거)

1. 프로필 구현 diff 에 `src/domain/sync/server-rules.vectors.ts`·`worker/**` **런타임 코드**·`src/infra/indexeddb/db.ts`(`DB_VERSION`)·D1 마이그레이션 변경이 **없다**(테스트 파일 `worker/sync/apply.test.ts` 에 "프로필 세 필드가 푸시→저장→풀 왕복에서 살아남는다" 1건 추가는 권장).
2. 상한 상수(이름 20·소개 60·사진 16,384자·허용 MIME 접두)는 `src/domain/profile/profile.rules.ts` **한 곳**에만 리터럴로 있고, 클라이언트 검증·백업 복원·동기화 풀·Worker 푸시가 전부 그 상수를 import 한다.
3. 백업 복원·동기화 풀·Worker 푸시 **세 곳**(같은 `readSettings`)은 형식이 틀린 `profile*` 필드를 **버리고 행은 통과**시키며, 유효한 값은 **받은 그대로**(다듬지 않고) 저장한다 — 테스트가 "잘못된 `profileAvatar` + 유효한 나머지 → 행 채택, 필드 없음" 과 "앞뒤 공백 있는 이름 → 파일 값 그대로" 를 고정한다.
4. 프로필 쓰기는 저장소에서 **새로 읽은** `Settings` 행 위에 `touch` 한 결과만 `upsert` 하고, 같은 틱에 두 설정 저장을 시작하지 않는다 — 캐시된 옛 행으로 다른 필드를 덮는 회귀 테스트(테마가 먼저 바꾼 강조색이 살아남는다)가 있다.
5. 사진 처리는 클라이언트에서만 하고 결과 문자열이 상한을 넘으면 저장하지 않는다(품질 하한에서 멈추고 오류 — 무한 루프 없음).
6. **Worker 재배포 = T-G 출시 조건.** 확장된 `SETTINGS_KEYS` 를 담은 Worker 가 배포되기 전에는 프로필을 사용자에게 열지 않는다(실기기 두 대에서 이름이 넘어가는 것을 확인한 뒤 `implemented`).

## 재검토 트리거

- 사진 상한(16,384자)을 넘겨야 하는 요구(큰 아바타·배경 이미지)가 생긴다 → 객체 저장소 대안을 다시 본다.
- 공개(소셜) 프로필에 사진·소개를 얹고 싶어진다 → "복사해 공개" 를 별도 스펙 + ADR 로(ADR-0022 투영 원칙).
- `Settings` 동시 편집 경합 또는 혼합 버전(ㄹ)으로 프로필이 사라졌다는 보고가 실제로 들어온다 → 필드 단위 병합 또는 별도 행 분리를 검토.
