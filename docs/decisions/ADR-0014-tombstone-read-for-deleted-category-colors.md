# ADR-0014: 삭제된 카테고리의 색은 전용 조회 메서드 `listDeletedByIds` 로 읽는다 (ADR-0007 결정 4 개정)

- 상태: accepted
- 날짜: 2026-09-16
- 관련: ADR-0007 결정 4(**개정** — supersede 아님, 나머지 결정은 그대로) · ADR-0009 규칙 4 · `docs/specs/date-strip.md` R7 · 티켓 T-26

## 맥락

date-strip R7 은 점 색을 "**종료·삭제된 카테고리 포함**, 활성 `order` 순 → 종료 → 삭제됨" 으로 세라고 한다. 사용자가 명시적으로 요구한 "카테고리를 지워도 이미 체크한 투두는 남는다" 가 화면에서 보이려면 지워진 카테고리의 색이 렌더 경로에 닿아야 한다. 그런데 ADR-0007 결정 4 는 엔티티 레포지토리의 **모든** 조회에서 툼스톤을 빼고, 툼스톤 읽기를 `DatasetRepository.readAll`(백업 전용) 하나로 몰아 두었다. 결과적으로 T-09 는 색을 모르는 점을 중립색 `--color-faint` 로 찍었는데 대비가 **1.97:1** 이라 사실상 보이지 않으면서 3칸뿐인 자리를 먹어 보이는 카테고리를 밀어냈고(리뷰 실측), 라운드 1에서 점 자체를 뺐다. 그 사이 R7 은 미충족이었다.

## 결정

**`CategoryRepository` 에 툼스톤만 돌려주는 전용 메서드 `listDeletedByIds(ids)` 하나를 더한다. 조회 메서드에 `includeDeleted` 같은 플래그는 만들지 않는다.**

1. ADR-0007 이 `includeDeleted` 를 기각한 근거는 **"MVP 에 호출처가 없다"** 였다. R7 이 호출처다 — 그 전제가 더는 참이 아니므로 결정 4 의 "툼스톤은 조회 API 밖에 있다" 를 "툼스톤은 **이름이 그렇게 말하는 메서드 밖에** 있다" 로 좁힌다. 같은 ADR 이 이미 탈출구를 적어 뒀다: _"필요해지면 옵션이 아니라 별도 메서드"_, 그리고 재검토 트리거의 _"`listDeleted` 별도 메서드가 1안이다(그래야 `READS` 전수 대조가 그대로 산다)"_.
2. 시그니처는 `listDeletedByIds(ids: readonly CategoryId[]): Promise<Category[]>` — **`ids` 중 툼스톤인 것만** `id` 오름차순으로. 살아 있는 로우는 **절대** 나오지 않는다. 그래서 이 메서드는 `getById`·`list` 를 대신할 수 없고, "전량 주세요" 형태가 아니라 호출처가 id 를 알고 있을 때만 쓸 수 있다.
3. 호출처는 `useWeekSummaries` 하나다. `list({ includeClosed: true })` 로 살아 있는 목록을 먼저 읽고, **거기서 못 찾은 id 만** 모아 한 번 더 묻는다 — 지워진 카테고리를 참조하는 투두가 없으면 두 번째 조회는 나가지 않는다. 순서(활성 → 종료 → 삭제됨)는 여전히 도메인 `sortCategoriesForDisplay` 한 곳이 정한다.
4. 필터 위치(ADR-0007 결정 5)는 유지한다. 구현은 `memory/live.ts`·`infra/indexeddb/query.ts` 의 새 헬퍼 `deletedByIds` 를 거치고, **이름에 `live` 가 없는 것**이 "여기는 툼스톤이 나온다" 는 표식이다(`allRows`·`clear`·`bulkPut` 과 같은 규약). IndexedDB 쪽은 기본 키 `bulkGet` 이라 전수 스캔이 없다.

## 대안과 기각 이유

| 대안                                             | 기각 이유                                                                                                                                                                                                                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `list({ includeDeleted: true })` 플래그          | 조회 메서드 **전체**의 계약이 "툼스톤이 나올 수도 있다" 로 흐려진다. 호출처에서 툼스톤 여부가 보이지 않고, 기본값 실수의 통로가 된다(ADR-0007 이 이미 적은 이유). 계약 테스트의 `READS` 전수 대조도 "이 메서드는 어느 옵션에서 툼스톤을 감추는가" 를 더는 한 줄로 말할 수 없다 |
| `listDeletedByIds` 가 살아 있는 로우도 함께 반환 | 이름이 "삭제됨" 인데 살아 있는 값이 섞이면 일반 조회의 대용으로 쓰기 시작한다. 반환값이 항상 툼스톤이어야 계약 테스트가 "살아 있는 값은 절대 안 나온다" 를 단언할 수 있다                                                                                                      |
| `DatasetRepository.readAll()` 재사용             | 네 테이블 전량을 읽는다(ADR-0009 가 호출처를 백업으로 제한한 이유). 점 하나 그리려고 데이터셋 전량을 읽으면 스트립이 데이터 크기에 비례해 느려진다                                                                                                                             |
| 스펙 R7 을 고쳐 삭제된 카테고리를 빼기           | 사용자가 남긴 기록이 화면에서 사라진다. 레퍼런스 앱과의 사용감 목표에서 3단 정렬은 그 일부다                                                                                                                                                                                   |
| 중립색 점 유지                                   | 대비 1.97:1 로 보이지 않으면서 3칸 중 하나를 먹는다(실측) — 적극적으로 해롭다                                                                                                                                                                                                  |

## 결과

- 좋은 점: 렌더 경로에서 **툼스톤을 읽는 메서드가 호출처 문법에 드러난다**(`categories.listDeletedByIds(missing)`). 계약 테스트의 `READS` 전수 대조가 그대로 산다 — 새 메서드는 `Exclude<keyof CategoryRepository, 'upsert' | 'listDeletedByIds'>` 한 줄에서 **이름으로** 빠지므로, 툼스톤을 내는 조회를 또 만들려면 그 줄을 고쳐야 하고 그 diff 는 리뷰에 보인다. 음성 대조: 두 구현이 툼스톤을 빼도록 되돌리면 계약 6건 + 렌더 경로 2건이 죽는다(실측).
- 감수하는 점 1: **남용을 막는 것은 타입이 아니라 이름과 리뷰다.** `listDeletedByIds` 는 어떤 feature 코드에서도 부를 수 있고 린트가 막지 않는다. 막는 것은 (a) 살아 있는 로우가 나오지 않아 일반 조회를 대신할 수 없다는 점, (b) `ids` 를 요구해 "전량 주세요" 가 불가능하다는 점, (c) `READS` 의 `Exclude` 한 줄뿐이다. 이 문장이 이 ADR 이 약속할 수 있는 정확한 경계다.
- 감수하는 점 2: 지워진 카테고리를 참조하는 투두가 한 건이라도 보이는 주에는 카테고리 조회가 **2회**가 된다(순차). 첫 조회 결과를 봐야 물어볼 id 가 정해지므로 병렬로 만들 수 없다. 대신 그렇지 않은 주에는 0회다.
- 감수하는 점 3: 두 조회 사이에 카테고리 상태가 바뀌면(삭제·복구) 그 주의 점이 한 프레임 어긋날 수 있다. 다음 조회에서 맞춰지고 트랜잭션으로 묶을 만한 값이 아니다.

## 지켜야 할 규칙 (검증 가능한 문장 — 리뷰 판정 근거)

1. 엔티티 레포지토리의 조회 중 툼스톤을 반환하는 것은 **이름에 `Deleted` 가 있는 메서드뿐**이다. 플래그·옵션으로 툼스톤을 여는 시그니처는 리뷰 Blocker.
2. `listDeletedByIds` 의 반환 원소는 **전부 툼스톤**이다(계약 테스트가 단언). 살아 있는 id 만 넘기면 빈 배열이다.
3. 새 툼스톤 조회를 추가하려면 `category-repository.contract.ts` 의 `ReadName` `Exclude` 를 고쳐야 한다 — 그 줄 없이 추가하면 `READS` 전수 대조가 `TS1360` 으로 막는다.
4. ADR-0007 결정 4 의 나머지는 그대로다: `getById`·`list` 는 어떤 옵션으로도 툼스톤을 내지 않고(계약 테스트가 함께 단언), Phase 2 동기화는 여전히 별도 인터페이스로 읽는다.

## 재검토 트리거

- 툼스톤을 읽어야 하는 렌더 경로가 **둘째**로 생기면(예: 통계 화면의 삭제된 카테고리 막대) `ids` 기반이 맞는지, 아니면 `listDeleted()` 전량형이 필요한지 다시 본다.
- Phase 2 동기화 ADR 이 `SyncRepository.listChangedSince` 를 정의할 때 이 메서드가 그쪽으로 흡수되는지 본다.
